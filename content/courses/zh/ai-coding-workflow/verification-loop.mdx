大多数“AI 说做完了”的事故，都发生在最后一次命令与最后一句总结之间。模型确实跑了测试，只跑了它挑的那个文件；或者跑了失败，然后在总结里写成“测试基本通过”。验收环节要做的不是再加一句“记得跑测试”，而是把完成定义成一段可检查的输出。

## 把验收从请求搬到流程里

“请确保测试通过”是一句请求，模型可以打折执行。把它变成流程，需要两样东西：`AGENTS.md` 里的验证要求，和一条固定入口的命令。会话结束的条件是命令输出，不是自然语言的总结。

```md
<!-- .opencode/commands/verify.md -->

---
description: Run the verification suite and explain any failure
---

按以下顺序验证当前改动，全部使用真实命令，不要凭记忆推断结果：

1. `bun typecheck`
2. `bun test <受影响测试文件的路径>`
3. 全部通过后再跑 `bun test`（全量）

任何一步失败，停下来按下面的格式输出，不要继续修改代码：

- 失败断言原文（逐字复制，不转述）
- 涉及文件与行号
- 归因：环境 / 实现 bug / 测试过期 / 需求理解偏差
- 最小修复方案，以及修完要复跑的那一条命令

当前改动范围：

!`git status --short`
```

`!` 与反引号之间的内容会在提交提示词前执行并把输出注入，所以模型拿到的是真实的改动文件列表，而不是它以为的列表。这类 shell 块在命令求值时运行，不在工具权限流程内，只写可信命令。

## 失败解释要能复现，不能是转述

模型最省力的写法是“测试失败了，原因是类型不匹配，已修复”。这句话没有任何可核对的信息。要求它按四段输出，你就能判断它到底读没读报错。

| 要素 | 合格标准 | 不合格表现 |
| --- | --- | --- |
| 断言原文 | 逐字复制失败行与错误码 | “有个断言没过” |
| 位置 | 文件与行号，含调用链 | “在测试文件里” |
| 归因 | 落到四类之一，并说明证据 | “可能是环境问题” |
| 下一步 | 一条具体命令加预期结果 | “再跑一次应该就好了” |

只有第三段能定性，第四段才能执行。缺任何一段，就让它重做，而不是自己接手——接手一次，下次它还会省掉这段。

## 归因分类决定允许的动作

同一句“测试失败”，背后该做的事完全不同。把分类写进规则，模型就不会用改测试的方式绕过实现 bug。

- **环境**：依赖没装、端口占用、数据库未启动。允许的动作是修环境或说明阻塞；禁止改代码去迁就。
- **实现 bug**：断言正确、代码错误。允许改实现，禁止动断言。
- **测试过期**：断言与现行规格冲突。只有能指出规格出处时才允许改测试，否则先提问。
- **需求理解偏差**：实现符合测试但不符合需求。停下来对齐需求，不要两边一起改。

对应地，把“不得为变绿而弱化断言”写成常驻规则，比每次口头强调可靠：

```md
## Verification
- 完成前必须运行 `bun typecheck` 与相关测试，并贴出命令与输出。
- 不删除、跳过或弱化断言来让测试通过。
- 测试失败时先给归因，再给最小修复，不要顺手重构。
- 无法判断归因时停下来提问，不要猜测。
```

## 非交互场景要提前配好权限

在 CI 或脚本里用 `opencode run "运行 bun test 并只汇总失败用例"` 时，没有界面可以点批准。文档说得很清楚：非交互式客户端必须自行决定如何处理批准请求，而配置的 `deny` 始终生效。所以测试命令要预先 `allow`；否则非交互执行只能自行决定，结果不可预期。

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "permissions": [
    { "action": "shell", "resource": "*", "effect": "ask" },
    { "action": "shell", "resource": "bun test *", "effect": "allow" },
    { "action": "shell", "resource": "bun typecheck *", "effect": "allow" },
    { "action": "shell", "resource": "git push *", "effect": "deny" }
  ]
}
```

先跑单文件、再跑全量，是这套循环里最省时间的习惯：单文件几秒出结果，全量留给收尾。

## 落地动作

1. 写 `/verify` 命令：`mkdir -p .opencode/commands && $EDITOR .opencode/commands/verify.md`，把上面的模板填成你仓库的真实命令。
2. 在 `AGENTS.md` 加一段 `## Verification`，写明必跑命令与“不许弱化断言”。
3. 故意改坏一个断言跑一次 `/verify`，观察模型是否逐字贴出失败原文；没有就补一句“逐字复制，不转述”。
4. 在 `opencode.jsonc` 里为测试与类型检查加窄口径 `allow`，同时 `deny` 掉 `git push *`。

## 常见坑

- **现象**：模型总结“测试通过”，但仓库里明明有失败用例。 → **原因**：只跑了局部文件，或根本没跑。 → **对策**：要求贴命令与输出原文，输出里出现失败行即视为未完成。
- **现象**：修完测试变绿，功能却仍然不对。 → **原因**：模型改了断言去迁就实现。 → **对策**：规则里禁止弱化断言，并要求改测试前先指出规格出处。
- **现象**：CI 里 `opencode run` 卡住不动。 → **原因**：测试命令命中了 `ask` 规则，非交互环境没有人能批准。 → **对策**：把固定命令改成 `allow`，宽泛规则留在前面，`deny` 放最后。
