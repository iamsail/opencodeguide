直接让 AI 动手，最常见的结局是它一边猜需求一边改文件：先改了三个文件，发现方向不对，再回头改另外两个，最后你 review 的其实是一段没人设计过的代码。问题不在模型笨，而在任务从没被拆成“想清楚”和“写下来”两段。

Plan Mode 提供的就是这个停顿点。它把“读与想”和“写”分开，你审方案的代价远低于审一屏 diff。

## Plan Mode 限制的是写，不是想

`plan` 是内置的主智能体，职责是在不编辑普通项目文件的前提下探索与规划。它照常读代码、搜索、执行受权限控制的 shell 命令，但你不会在它手里看到一屏突然出现的修改。

| 在 plan 里可以做 | 在 plan 里做不了 |
| --- | --- |
| 读文件、grep、看目录结构 | 编辑或写入项目文件 |
| 运行只读命令，如 `git log`、`bun test` | 生成补丁、批量改文件 |
| 写出方案、列出待改文件与验收命令 | 顺手把方案实现掉 |
| 写入 OpenCode 的 plan 文件 | 改动仓库里的代码 |

默认权限里，`plan` 拒绝编辑，`~/.opencode/plan` 下的文件除外，shell 仍按你的权限规则执行。切换方式有两种：按 **Shift+Tab** 循环智能体或在 TUI 里运行 `/agents`；也可以让命令自己指定智能体，这更适合团队统一入口。

边界要理解准确：plan 不是“更安全的模型”，它只是当前智能体没有编辑权限。切回 `build` 之后写能力立刻恢复，所以“先方案后代码”靠的是流程，不是这层限制。

## spec 落在仓库里，方案才不会随会话消失

plan 写入的位置在 `~/.opencode/plan`，属于你本机的 OpenCode 目录，不在仓库里。会话关掉、换台机器、换个人接手，这份方案就没了。所以真正的交付物应该是仓库里的 spec 文件，plan 只负责把它推敲出来。

```md
<!-- docs/specs/checkout-idempotency.md -->

# 结算接口幂等

## 目标
`POST /checkout` 在相同 `Idempotency-Key` 下重复调用只创建一笔订单。

## 非目标
- 不改支付网关的重试逻辑。
- 不动 `orders` 表已有字段，不写历史数据回填。
- 不重构 `src/checkout/` 之外的文件。

## 改动点
- `src/db/schema/idempotency.ts`：新增 key 表。
- `src/checkout/handler.ts`：入口查 key，命中则返回上次结果。
- `test/checkout/idempotency.test.ts`：重复请求断言只落一单。

## 验收
- `bun test test/checkout/idempotency.test.ts`
- `bun typecheck`

## 回滚
删除新增表与 handler 中的查询分支即可，无数据迁移。
```

“非目标”这一节比“目标”更能约束模型。没有它，模型会把“顺便优化”当成善意；有了它，超出范围的改动就是明确违规，你可以直接退回。

## 用命令把流程固定成入口

每次手打“先别写代码，给我方案”既费事又容易漏约束。做成命令，智能体和约束一起固化：

```md
<!-- .opencode/commands/spec.md -->

---
description: Draft an implementation spec without editing files
agent: plan
---

阅读 `$ARGUMENTS` 与相关代码，产出实施方案：

1. 列出要改的文件及每个文件改什么，不写代码。
2. 给出每条改动的验收命令。
3. 指出风险点与回滚方式。
4. 如果 spec 的信息不足以决定方案，先提出问题，不要假设。
```

`agent: plan` 会让命令在提交提示词前把当前会话切到 plan，`$ARGUMENTS` 收到 spec 路径。于是 `/spec docs/specs/checkout-idempotency.md` 就是一个只能出方案、不能落地的入口。方案本身要求落回仓库文件，别只留在会话里。

## 审方案只看三个问题

拿到方案不要从头读到尾，按三个问题过：

1. 每个改动文件都能对应到 spec 的“目标”或“改动点”吗？对不上就是越界。
2. 每条改动都有可执行的验收命令吗？没有就是不可验收。
3. 出问题时怎么退回去？没有回滚路径就先补。

三个问题都过了，再按 **Shift+Tab** 切回 `build`，把 spec 路径贴进提示并追加一句“偏离 spec 时停下来提问，不要自行扩大范围”。执行阶段允许它读 spec、跑验收命令，但方向由 spec 决定，不由它临场判断。

## 落地动作

1. 建目录：`mkdir -p docs/specs .opencode/commands`。
2. 挑一个改动涉及三个以上文件的任务，按上面的模板写 `docs/specs/<slug>.md`，重点补“非目标”。
3. 建 `/spec` 命令并运行一次，检查方案里的改动文件是否全部落在 spec 范围内。
4. 用三个问题审方案，通过后切回 `build` 执行，结束前逐条跑验收命令。
5. 把 spec 提交进仓库，让下一个人接手时能看见当时的边界。

## 常见坑

- **现象**：说好了只出方案，模型还是改了文件。 → **原因**：当前会话仍是 `build` 智能体，plan 没被选中。 → **对策**：用 `/agents` 或 **Shift+Tab** 切到 plan，或在命令 frontmatter 写 `agent: plan`。
- **现象**：方案里塞进了“顺便重构缓存层”，实施时范围失控。 → **原因**：spec 缺“非目标”。 → **对策**：先把不做的事写死，再让模型出方案。
- **现象**：第二天继续做，发现方案找不到了。 → **原因**：方案只存在于 plan 写入的 `~/.opencode/plan`，不在仓库。 → **对策**：结论必须落成 `docs/specs/` 下的文件。
