同样一个模型，有人用起来像可靠的同事，有人用起来像随机改代码的脚本。差别很少在提示词技巧，而在任务本身是否成立：上下文是否够用、需求是否可判定、完成是否有标准。

下面三种反模式几乎覆盖了失败任务的大多数。它们的共同点是——看起来都在“多给一点信息”，实际把判断责任推给了模型。

## 反模式一：过度上下文

典型动作是把整个仓库、十几个文件、几百行日志一起塞进提示。出发点是“信息越多越准”，结果是约束被稀释：真正关键的那句“不要改公开 API”淹没在无关代码里，模型开始引用与任务无关的模块，token 成本还会随每次追问重复。

上下文只该有三类内容：入口文件（请求从哪里进来）、契约定义（类型、接口、表结构）、失败证据（报错原文或复现命令）。其余代码让智能体自己找——内置的 `explore` 子智能体就是干这个的，它以只读方式搜索代码，不编辑文件，适合在动手前定位“这个逻辑到底在哪个文件里”。

| 反模式 | 典型说法 | 真实代价 | 替换写法 |
| --- | --- | --- | --- |
| 过度上下文 | 一次性 `@` 十几个文件 | 约束被稀释，模型引用无关代码 | 只给入口、契约、报错原文 |
| 伪需求 | “把这段优化一下” | 无判定标准，产出靠猜 | 现状 + 目标 + 边界 + 不做 |
| 无验收标准 | “改完告诉我” | 完成靠模型自述 | 附一条能跑的命令与期望输出 |

还有一个副作用值得知道：上下文过长会触发压缩，早期贴进去的细节可能被摘要掉，你以为给全了，模型看到的反而是删减版。

## 反模式二：伪需求

“优化一下性能”“让代码更清晰”“重构这部分”——这类需求的问题不是模糊，而是没有判定标准。模型会找一个它认为合理的解释去做，你 review 时才发现方向从一开始就不同。

改写的公式很固定：现状是什么、目标是什么、边界在哪、明确不做什么。例如把“优化结算接口”改成“结算接口在并发下出现超时，日志指向 `handler.ts` 里的逐单查询；改成一次批量查询，不改响应结构，不改路由”。目标、位置、手段、禁区齐全，模型才有可能做对。

判断一条需求是否成立，可以试着反向写验收：如果你写不出“什么现象算做完”，那它还不是需求。

## 反模式三：没有验收标准的任务

没有验收命令时，模型的“已完成”只是文本。它可能漏跑测试、只改了主路径、或者把失败归因于环境而不验证。你花在复核上的时间，比自己做还长。

对策是每条任务都附一条可执行命令和一句期望结果，并且要求它贴出真实输出。命令要能被机器判定：测试通过、类型检查无错误、某接口返回指定状态码，而不是“看起来正常”。

```md
<!-- 任务卡：任何一次改动都按这五段写 -->

## 现状
`POST /checkout` 重复提交时创建多笔订单，复现：`bun test test/checkout/duplicate.test.ts`

## 目标
相同 `Idempotency-Key` 的重复请求返回首次结果。

## 边界
只改 `src/checkout/`，不动路由与响应结构，不改支付网关调用。

## 不做
不加缓存，不改 `orders` 表结构。

## 验收
`bun test test/checkout/duplicate.test.ts && bun typecheck` 全部通过，并贴出输出。
```

## 落地动作

1. 把任务卡存成命令：`mkdir -p .opencode/commands && $EDITOR .opencode/commands/task.md`，之后用 `/task <描述>` 起任务。
2. 从 backlog 里挑三个任务，按五段模板重写，写不出验收命令的那个先不做。
3. 下次遇到“这个逻辑在哪”的问题，先说“用 explore 子智能体定位 `X` 的实现位置”，再让它读文件，避免一次贴一堆代码。
4. 复盘一个失败任务，标出它属于哪类反模式，把改写后的版本记进 `AGENTS.md` 或团队笔记。

## 常见坑

- **现象**：贴了大量代码，模型仍改错关键约束。 → **原因**：约束被埋在代码中间，没有出现在提示开头。 → **对策**：把“不要动 X”提到第一句，代码随后。
- **现象**：模型宣布完成，功能却没有变化。 → **原因**：任务没有验收命令，完成标准由模型自述。 → **对策**：每条任务附命令与期望输出，要求贴原文。
- **现象**：需求描述越写越长，实施仍然跑偏。 → **原因**：把背景资料当成了需求，缺少可判定目标。 → **对策**：用“非目标”删减，只保留一个可验证结果。
