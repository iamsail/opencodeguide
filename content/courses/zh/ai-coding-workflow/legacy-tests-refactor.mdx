「这个函数没测试，你直接重构，保证行为不变」是遗留代码里最贵的一句委托。模型能读懂实现，读不懂线上数据里沉淀的历史行为；没有基线，你和它都无法证明重构前后等价。补测试这一步本身也要被约束，否则 AI 会用「测试全绿」掩盖它顺手改掉的边界。

## 用特性测试冻结现状，而不是定义正确

特性测试的原则是断言当前输出，哪怕它看起来像 bug；修 bug 是另一次提交，两件事混在一起就再也分不清哪次改动引起回归。先让 Plan Mode 只读盘点，把对外可观测的行为列成清单：返回值、抛出的异常、写入的表与字段、调用的外部 HTTP，然后按清单写测试。

```bash
git switch -c chore/pin-billing-behavior
opencode run --agent plan "只读分析 src/billing。列出对外可观测行为：返回值、抛出的错误类型、写入的表与字段、调用外部 HTTP 的位置与顺序。不要修改任何文件。"
```

清单里凡是你无法用一句话判定「变还是没变」的条目，都不要立刻写进测试——那说明这个行为还没被理解，先读懂再锁。

## 测试锁接口，不锁实现

锁实现的测试会在重构中集体报错，让你误以为改坏了，进而放弃重构。这三条约束能避免大部分假失败：只调用模块的公开入口；不 mock 被重构对象自己的内部函数；mock 只出现在进程边界（数据库、HTTP、时钟、随机数）。

| 该锁住 | 不该锁住 |
| --- | --- |
| 公开函数对给定输入的返回 | 私有 helper 的调用次数 |
| 抛出的错误类型与消息关键字 | 内部 SQL 的拼接顺序 |
| 写入了哪些表、哪些字段 | 日志文案的完整字符串 |
| 边界输入：空值、0、超长字符串 | 实现里的循环次数 |

## 分批重构，每批留一次后悔的机会

一次会话只改一个函数或一个文件，改完立刻跑对应测试并提交。提交才是真正的回滚点；`/undo` 只是便利功能，它恢复的是活动目录里被助手步骤改过的路径，需要 Git 仓库，shell 造成的副作用（写库、发请求、改被忽略的产物）不会被撤销。所以动代码前先把现有改动提交掉。

```bash
npm test -- src/billing
git add -A && git commit -m "refactor(billing): extract tax rounding"
```

上面的测试命令依赖你项目里的 test script，换成真实命令并写进 AGENTS.md，别让模型猜。

## 让 AI 自己证明测试有效

测试写完做一次变异检查：手动把被测逻辑改坏一行，跑测试确认变红，再还原。这一步筛掉的是「永远通过」的假测试，比再补十条断言有用。

在 AGENTS.md 里写三条硬规则，让每个会话都继承：

- 修改 `src/billing` 前先读该目录的 AGENTS.md 与已有测试。
- 每次重构后运行 `npm test -- src/billing`，并在回复中贴出尾部输出。
- 测试失败时先解释失败原因，不要直接改断言。

## 落地动作

1. 建分支，让 Plan Mode 产出行为清单并存成 `docs/billing-behavior.md`，这是你后面判断「改坏了没有」的唯一依据。
2. 按清单写 3 条特性测试，跑通后单独提交一次，让这次提交只包含测试。
3. 把验证命令和「失败先解释」写进 AGENTS.md，再开始第一批重构，每批一次提交。

## 常见坑

- **现象**：AI 补的测试一次全绿，重构后也全绿，但线上出错 → **原因**：测试断言复制了当前实现的输出，等于把 bug 也锁成了预期 → **对策**：做变异检查，改坏一行确认测试会红，并补空值、0、超长输入三类边界。
- **现象**：重构越改越大，想整体回滚 → **原因**：一次会话改了多个文件，中间没有提交 → **对策**：按文件分批，每批一次提交；`/undo` 只当辅助，不替代提交。
- **现象**：`/undo` 之后文件没恢复 → **原因**：文件在活动目录之外、被 Git 忽略，或当前不在 Git 仓库里 → **对策**：在目标目录内启动会话，并确保改动纳入了版本控制。
