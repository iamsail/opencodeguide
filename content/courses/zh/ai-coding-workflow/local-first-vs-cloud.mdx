把 OpenCode 当成「云端助手」是第一个误解：它跑在你自己机器上，读文件、执行 shell、写会话记录都由本地进程完成，真正离开机器的只有发给模型的请求体。这条边界不清楚，安全评审会问错问题，成本估算也会算错对象。

## 边界在哪：本地编排，远端推理

OpenCode 默认为你启动一个共享后台服务，会话、配置、权限判定与工具执行都归它管，只有模型请求发往外部。用 `opencode --standalone` 可以换成私有服务，但编排仍然在本机。

所以安全评审的正确问法不是「它会不会上传我的仓库」，而是「哪些内容被我放进了上下文」。文件不会自动同步，但一旦被读进会话历史，之后每一轮请求都可能重发它。

| 数据 | 位置 | 说明 |
| --- | --- | --- |
| 代码文件、git 历史 | 本机 | 只有被读入上下文的部分出现在请求里 |
| 会话记录与凭据 | 本机 SQLite，`~/.local/share/opencode/opencode.db` | 凭据通过 `/connect` 或 `auth` 管理 |
| 提示词、文件片段、shell 输出 | 请求体 | 发给提供商，受其数据条款约束 |
| 推理与模型权重 | 提供商机房，或你的 GPU | 用 Ollama 等本地服务时不出网 |

敏感仓库里，`git log`、`.env` 的搜索结果、内部接口返回都是高风险面：它们不需要你主动上传，只要被 `!` 或工具执行一次就进了上下文。

## 成本不是一个单价，是三种计费面

三张账单的行为完全不同，只比月费会掩盖差异。

| 计费面 | 何时划算 | 隐性成本 |
| --- | --- | --- |
| 自有硬件（Ollama、vLLM） | 高频、短上下文、代码敏感 | 显存与吞吐有上限，长任务排队，运维归你 |
| 订阅（如 OpenCode Go） | 每人每天稳定用量 | 超出额度另计，可选模型受限 |
| 按量 API | 突发需求、需要前沿模型 | 长会话把输入侧开销不断放大 |

团队做预算时，用「一个 PR 生命周期消耗多少 token」估算，比比较月费单价可靠得多，因为它把上下文长度、重试和压缩都算进去了。

## 用配置把边界写死

策略比口头约定可靠：先声明全拒，再逐个放行，把「换回云端」变成一次需要改配置、走评审的动作。

```jsonc title="opencode.jsonc"
{
  "$schema": "https://opencode.ai/config.json",
  "model": "ollama/gemma3:4b",
  "policies": [
    { "action": "provider.use", "resource": "*", "effect": "deny" },
    { "action": "provider.use", "resource": "ollama", "effect": "allow" }
  ],
  "permissions": [
    { "action": "shell", "resource": "git push *", "effect": "ask" },
    { "action": "shell", "resource": "rm -rf *", "effect": "deny" }
  ]
}
```

权限段管的是工具能不能执行，策略段管的是哪个提供商能不能被使用，两者不能互相替代：只 deny 提供商，`shell` 照样能跑；只设权限，模型请求照样出境。这份文件提交进仓库，边界变化就会出现在 diff 里。

## 云端仍然值得的四个场景

- 跨十几个文件的重构与长上下文审查，前沿模型的稳定性仍明显占优。
- 架构决策、疑难 bug，需要最强推理而不是最快响应。
- 团队没有 GPU 运维能力，本地模型的服务质量与升级成本会吃掉省下的钱。
- 合规允许，且你确认过提供商的数据使用条款。

本地优先适合的场景正好相反：高频小改动、补测试、读代码，以及不允许出网的仓库。

## 团队分层：默认、例外、兜底

三层足够覆盖多数团队：默认模型选本地或按量 API 里最便宜的那档；例外是敏感仓库，用 `policies` 全拒后只放行本地提供商；兜底是 Console 的预算策略，按工作区、成员或服务账户设月度上限，超限请求返回 HTTP `429`，而不是等到月底看账单。

免费模型与套餐内的 Go 用量不计入预算，别拿它当配额管理。

## 落地动作

1. 在仓库根目录创建 `opencode.jsonc`，先只写 `$schema` 与 `model`，运行 `opencode` 后用 `/models` 确认该模型可见。
2. 加入上面的 `policies` 白名单与两条 `permissions`，`git diff` 检查后提交，并在 PR 描述里说明为什么选这个提供商。
3. 在 Console 的 Controls 里加一条工作区月度 Budget，金额设为上月实际支出的 1.2 倍。

## 常见坑

- **现象**：以为「本地优先」等于断网可用，结果 `opencode` 打开后没有可选模型。 → **原因**：OpenCode 只是把编排放在本地，推理仍要指向某个端点；本地模型也需要服务在跑。 → **对策**：保持 `ollama serve` 常驻，用 `/models` 确认出现 `ollama/...` 条目，并把默认模型写成该引用。
- **现象**：配置了 `policies` 仍能用云端模型。 → **原因**：更靠近工作区的 `.opencode/opencode.json` 或系统级配置覆盖了项目文件，且策略的求值顺序与普通配置相反。 → **对策**：全仓库统一只用一种配置形式，用 `opencode debug paths config` 确认实际生效的配置目录。
- **现象**：本地模型能对话，但一让它改代码就乱改。 → **原因**：小参数模型的工具调用与上下文能力不足，OpenCode 从 Ollama 读到的能力只是服务端声明。 → **对策**：给本地模型显式设置 `capabilities` 与 `limit`，或只让它承担检索、总结类子任务。
