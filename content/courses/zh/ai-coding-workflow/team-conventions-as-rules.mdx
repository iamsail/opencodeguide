翻开多数团队的规范文档，写的是“遵循现有命名风格”“补充必要测试”“提交信息要清晰”。这三句话对人尚且要靠 review 兜底，对模型几乎等于没写——它不知道“现有风格”指哪份文件，也不知道“必要”到什么程度。

可执行的规则有三个特征：给出具体路径或正反例，绑定一条能跑的命令，规定违反时该停下来问谁。缺一个，模型就只能靠猜，而你会在 review 里反复看见同样的意见。

## 先判断这条规则能不能被判定

改写之前先问一句：给我两个产出物，我能不能不看解释就分出对错。能，它就该写成模式或命令；不能，它就不是规则，只是愿望。

| 模糊说法 | 可判定写法 | 落点 |
| --- | --- | --- |
| 保持命名一致 | 文件名 `kebab-case`，组件导出 `PascalCase` | `AGENTS.md` |
| 记得补测试 | 同目录新增 `<name>.test.ts`，跑 `bun test <path>` 全绿 | `AGENTS.md` + 权限 |
| 提交信息写清楚 | `type(scope): subject`，body 写动机 | `.opencode/commands/commit.md` |
| 别乱改依赖 | 改 `package.json` 前先在回复里列出新增包与理由 | `AGENTS.md` |

## 命名：给模式和反例，不给形容词

命名是最容易机器化的约定，因为判定对象就是文件路径和标识符。写成下面这样，模型没有解读空间：

```md
## Naming
- 文件名用 kebab-case：`user-profile.ts`，不写 `UserProfile.ts`。
- 导出的 React 组件用 PascalCase：`export function UserProfile()`。
- 类型别名用 PascalCase，不加 `I` 前缀。
- 测试文件与被测文件同目录：`<name>.test.ts`。
- 新增文件前先 `ls` 该目录，沿用已有命名；不确定时在回复里提出，不要自创。
```

最后一条是关键补充：命名规则总有覆盖不到的新情况，与其让模型自由发挥，不如要求它显式提出。规则的作用不是穷举，而是把“猜”换成“问”。

## 测试：把“要补测试”绑到一条命令上

没有命令的测试要求无法验收，模型只能自称“已补充测试”。所以测试约定必须是两段式：写什么文件，用什么命令证明。

```md
## Tests
- 新增导出必须同目录新增 `<name>.test.ts`，覆盖正常路径与一个失败路径。
- 修 bug 先写能复现的失败用例，再改实现；顺序反了就在回复里说明原因。
- 不删除或弱化已有断言。确需修改，先在回复中指出与规格冲突的具体段落。
- 完成前必须实际运行 `bun test <path>` 并贴出输出。
```

改完规则还要放开权限，否则智能体每跑一次测试都要你点一次批准，人很快就会习惯性放行：

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "permissions": [
    { "action": "shell", "resource": "*", "effect": "ask" },
    { "action": "shell", "resource": "bun test *", "effect": "allow" },
    { "action": "shell", "resource": "bun lint *", "effect": "allow" },
    { "action": "shell", "resource": "git push *", "effect": "deny" }
  ]
}
```

权限是最后一条匹配的规则生效，所以宽泛的 `ask` 放在最前，具体允许跟在其后，禁止推送收尾。以 ` *` 结尾的模式同时匹配不带参数的命令，`bun test *` 对 `bun test` 和 `bun test src/a.test.ts` 都成立。

## 提交信息：用命令固定格式与输入

提交信息不适合塞进 `AGENTS.md` 做常驻规则，它只在收尾时用一次。做成命令，格式和输入一起固定：

```md
<!-- .opencode/commands/commit.md -->

---
description: Draft a commit message from staged changes
---

根据下面的已暂存改动起草提交信息：

- 格式 `type(scope): subject`，subject 不超过 50 个字符，不加句号。
- body 说明"为什么"，不复述 diff。
- 只输出提交信息本身，不要执行 `git commit`。

!`git diff --cached`
```

`!` 与反引号之间的 shell 输出会在提交提示词之前注入，所以模型看到的是真实的暂存内容，不必你手动粘贴；输入固定了，格式才不容易漂移。这类 shell 块在 OpenCode 求值命令时执行，不在工具权限流程之内，只写来自可信来源的命令。

## 落地动作

1. 翻最近两次 review，挑出重复出现最多的三条意见，逐条追问“能不能不看解释判对错”。
2. 把这三条写进根目录 `AGENTS.md`，每条附一个正例、一个反例或一条命令。
3. 建提交命令：`mkdir -p .opencode/commands && $EDITOR .opencode/commands/commit.md`，暂存一处改动后跑 `/commit` 看格式是否稳定。
4. 在 `opencode.jsonc` 里补窄口径的 `allow`（测试、lint）与 `git push *` 的 `deny`，再跑一次任务确认不再反复弹批准。

## 常见坑

- **现象**：规则改了三次，模型还是时对时错。 → **原因**：规则本身是形容词（“合理”“清晰”“一致”），没有判定入口。 → **对策**：每条规则必须能落到具体路径、正反例或命令上，落不下去就删掉。
- **现象**：同一条命名要求，`AGENTS.md` 和某个命令模板里的措辞不一致。 → **原因**：规则复制到了两处，改动时只改了一处。 → **对策**：单一来源，命令里只引用不重述。
- **现象**：为了少点几次批准，顺手用了“始终允许”，之后智能体自己跑起了更宽的命令。 → **原因**：已保存的批准会变成项目范围的 `allow` 规则，范围取决于工具提议的模式。 → **对策**：提前写好窄口径 `allow`，并定期清理不再需要的已保存批准。
