跨仓库改动的成本不在代码量，而在证据链。前端字段改了、后端接口没上、文档还在教旧字段——三处单独看都「完成」了，合起来就是线上 500。控制它的办法不是更努力地记住，而是把顺序固定下来，把检查做成命令。

## 一次会话只在一个仓库，快照不会跨仓库

文件快照覆盖的是会话活动目录里、Git 工作树中的文件。你在前端目录开会话，后端仓库的改动既不进快照，也不能靠 `/undo` 恢复；被 Git 忽略的文件、大于 2 MiB 的未跟踪文件同样不在范围内。跨仓库改动必须按仓库切开，各自独立会话、独立提交。

```bash
opencode ~/code/web-app
opencode ~/code/api-server
```

需要让一个会话读另一个仓库时，用 `external_directory` 精确授权，而不是把家目录整个放开。`read`、`edit` 与 `external_directory` 的 `~` 会在配置加载时展开，shell 资源不会。

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "permissions": [
    { "action": "external_directory", "resource": "~/code/api-server/*", "effect": "allow" },
    { "action": "read", "resource": "~/code/api-server/*", "effect": "allow" },
    { "action": "edit", "resource": "~/code/api-server/*", "effect": "deny" }
  ]
}
```

在前端会话里读后端，目的是核对字段的真实形状，不是顺手替别人改仓库。写完的编辑权限留到那个仓库自己的会话里。

## 顺序：后端的向后兼容先落地

字段改动是删除式还是并存式，决定了你会回滚一次还是两次。默认走并存：后端先加新字段并保留旧字段，前端切换读新字段，文档跟上，最后才删旧字段。

| 顺序 | 仓库 | 改动 | 通过条件 |
| --- | --- | --- | --- |
| 1 | api-server | 新增字段，保留旧字段 | 旧客户端回归测试通过 |
| 2 | web-app | 改为读取新字段 | 新旧字段并存时页面正常 |
| 3 | docs | 更新接口示例与迁移说明 | 全仓搜索无旧字段引用 |
| 4 | api-server | 删除旧字段 | 旧字段线上调用量归零 |

顺序搞反了，第 2 步就会让旧客户端读不到数据，而这类问题在本地很难复现。

## 用可执行检查代替「我记得同步了」

文档同步不能靠记忆。提交前跑一次全仓引用检查，输出非空就说明还有地方没改完：

```bash
grep -rn --include='*.md' --include='*.ts' --include='*.tsx' 'legacy_status' .
```

把这条命令写进 AGENTS.md 的验收段，模型每次收尾都会自己跑，比你口头提醒可靠。文档仓库如果有独立的 `instructions` 条目，也把「字段改动必须同 PR 更新接口示例」写进去。

## 落地动作

1. 在三个仓库各建同名分支 `feat/order-status-field`，先确认各自的基线测试是绿的。
2. 在前端会话里只读后端，列出接口实际返回的字段形状与文档描述的差异，形成一张对照表。
3. 按表格顺序改，每仓库单独提交，代码与文档进同一个 PR，最后才删旧字段。

## 常见坑

- **现象**：`/undo` 只恢复了前端，后端改动还在 → **原因**：快照范围限于会话活动目录，后端文件在范围外 → **对策**：每仓库独立会话，用提交回滚，别指望跨仓库快照。
- **现象**：授权了外部目录之后，模型直接改了后端仓库 → **原因**：只给了 `allow`，没补 `edit: deny`，而最后一条匹配的规则生效 → **对策**：外部目录默认只读，需要写时在那个仓库另开会话。
- **现象**：接口文档与实现不一致很久才发现 → **原因**：文档不在验收链路里，没有任何命令会失败 → **对策**：把 grep 引用检查写进 AGENTS.md，作为提交前的固定动作。
