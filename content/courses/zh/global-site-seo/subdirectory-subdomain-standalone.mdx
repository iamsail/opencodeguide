多语言站点的 URL 结构是最难改的一步：改一次要重配外链、重做 301、重跑分析，几个月内排名都回不到原点。所以要先想清楚再动手，而不是上线后觉得不好看再换。

## 结论先行：默认用子目录

理由不是「权重更高」，而是三件可核对的事实：子目录与外链、站内链接、品牌搜索共享同一主机名；部署只有一套；分析不用拆。只有三种情况值得考虑别的方案：本地团队要独立运营、法律要求本地实体与本地品牌、单个市场大到值得独立营销站点。

## 三种结构的对照

| 维度 | 子目录 `example.com/de/` | 子域 `de.example.com` | 独立域名 `example.de` |
| :--- | :--- | :--- | :--- |
| 信号归属 | 与主站同一主机名，历史合并 | 可分辨子域，历史分开记 | 完全从零，需重建认知 |
| 部署成本 | 一套代码一套部署 | 可按语言拆，配置分散 | 每站独立证书与监控 |
| 分析口径 | 一个属性看全部 | 需跨子域配置 | 多套属性，报告要合并 |
| 迁移代价 | 低（改路由 + 301） | 中（加子域 + 301） | 高（换域名 + 重做外链） |

「权重继承」的实际含义是：链接、点击、品牌搜索这些信号跟着 URL 走。换主机名等于把这些信号的历史切断，只能靠 301 传递一部分，而传递是有损的、需要时间，所以越晚改越贵。

## 静态导出站点怎么迁移

本仓库是 `output: 'export'` 的静态站，`next.config` 的 `redirects`、`rewrites` 在静态导出下不可用，301 只能在托管层做（Cloudflare Redirect Rules）。迁移后逐条验证：

```bash
# 逐条检查：是否只有一跳 301，且最终落到 200
while read -r old new; do
  code=$(curl -s -o /dev/null -w '%{http_code}' -I "https://example.com$old")
  loc=$(curl -s -o /dev/null -w '%{redirect_url}' -I "https://example.com$old")
  echo "$old -> $code $loc expected=$new"
done < redirects.txt
```

通过标准三条：状态码是 301（不是 302）；跳转目标等于预期新地址；最终返回 200。出现 301 → 301 的链式跳转就合并规则。

## 迁移清单：五件事按顺序做

1. 冻结旧 URL：迁移期间不再新增页面，避免边改边搬。
2. 建映射表：一行一个旧地址，写明新地址、是否保留、是否合并。
3. 托管层加 301：静态导出站只能在 Cloudflare 做，规则上线后先小批量验证再全量。
4. 更新站内链接：站内还指向旧地址的链接会形成 301 链，逐页替换。
5. 重提 sitemap 并观察：迁移后一周看索引替换比例，两个月看排名是否回位。

还有两个常被忽略的成本：Cookie 与登录态在换主机名后全丢，用户要重新登录；分析工具的历史数据会断层，报告要按「迁移前 / 迁移后」拆开看，否则会把断层误判成流量下滑。

## 落地动作

1. 写出语言清单与每个语言的目标市场，标注「是否真的需要地区差异」，只有差异真实存在才拆地区目录。
2. 按上表逐项打分，重点看部署成本与迁移代价；两项都超出承受范围就选子目录。
3. 若已在迁移，先写 `redirects.txt`（旧路径 → 新路径），跑上面的脚本，把 302 与链式跳转修掉再上线。

## 常见坑

- **现象**：为「国际化形象」每个国家一个域名，半年后运维撑不住。→ **原因**：把品牌策略当成技术选择，忽略固定运维成本。→ **对策**：先用子目录跑通，本地实体成立才上独立域名。
- **现象**：迁移后排名两个月没恢复。→ **原因**：大量 302、链式跳转，或新页内容缩水。→ **对策**：301 一跳到位，当天重提 sitemap。
- **现象**：子域上线后主站品牌词排名下滑。→ **原因**：同一主题被拆到两个主机名。→ **对策**：一个主题只在一个主机名承载，另一个用 301 归并。
