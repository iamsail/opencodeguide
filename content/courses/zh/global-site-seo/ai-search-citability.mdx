同一个问题，AI 概览里引用的是竞品的三段话，而你的页面排在前五。排名没掉，流量却在走——这是新模式下的典型错位：答案引擎不只看你排第几，它要在你的页面里找到一段能独立成立、可追溯、且与问题精确对齐的话。

可引用性不是玄学，它可以拆成三件可检查的事：内容能被读到，结构让段落可被切出来，事实密度让切出来的段落值得信任。

## 先确认内容能被读到

第一道门是抓取与渲染，正文必须存在于 HTML 里，而不是靠脚本注入；静态导出天然满足，纯客户端渲染的页面经常只剩骨架。第二道门是策略：答案引擎的抓取器是否被 robots.txt 挡住，是一个需要主动决定的事，而不是默认放过——想被引用就别把它们一并屏蔽，不想就清楚代价是彻底退出这个渠道。

还有一个容易忽略的点：一个 URL 只讲一个主题。把二十个问题塞进同一页，每个问题的上下文都被稀释，切出来的段落谁也不够完整。

## 结构：每节一个小结论，先答后解释

答案引擎摘取的粒度通常是段落或列表项，所以段落必须能被单独拿起来读。做法很朴素：小标题写成具体问题（「静态导出还能用图片优化吗」而不是「关于图片」），每个小节第一句直接给结论，后面再展开原因和例外。

列表和表格比长段落更容易被完整摘出，也更难被截断曲解。反过来，最糟的写法是把关键结论埋在第三段中间，前面两段全是背景——切出来既没有结论，也没有主语。

## 事实密度：把形容词换成可核验的值

可被引用的句子通常包含四要素：主体、数值、时间、口径。缺一个，句子就只是观点。改写不复杂，难的是你得真的有数据。

| 弱表述 | 可引用表述 |
| :--- | :--- |
| 加载速度很快 | 首页在 CrUX 移动端的 LCP 为 2.2s（2026-10 数据） |
| 支持多语言 | 提供中、英、日三种语言，分别在 `/zh/`、`/en/`、`/ja/` 子目录 |
| 很多开发者在用 | 截至 2026-11，公开注册账号 1,240 个 |
| 官方推荐这种做法 | Next.js 文档「Static Exports」一节要求 `output: 'export'` |

同一事实在全站只能有一个数字。产品页写 1,240、关于页写「上千」、旧文章还留着 800，这种自相矛盾会直接拉低可信度，而且很难靠改一处修好。

## 实体标记：让「你是谁」可查

答案引擎判断一段话是否可信，会看它挂在谁名下。三样东西要一致：正文里可见的作者与更新时间、页面 JSON-LD 里的 `author` 与 `dateModified`、作者信息页或 `sameAs` 指向的外部身份。三者对不上，等于告诉引擎这段内容没有明确来源。

```json
{
  "@context": "https://schema.org",
  "@type": "TechArticle",
  "headline": "AI 搜索时代的可引用性",
  "datePublished": "2026-11-01",
  "dateModified": "2026-11-19",
  "author": {
    "@type": "Person",
    "name": "作者姓名",
    "url": "https://opencodeguide.com/zh/about/"
  },
  "publisher": { "@type": "Organization", "name": "OpenCode Guide" }
}
```

## 落地动作

1. 挑三篇最有转化价值的页面，逐节检查小标题是否为具体问题、首句是否给出结论，改掉纯背景式开场。
2. 把每节里的形容词逐条换成带数值、时间和口径的句子，找不到数据的就删掉这句判断，别用模糊表述填空。
3. 统一作者与更新时间的来源，让正文、JSON-LD 与作者页读同一个字段，改完抽查三个页面。

## 常见坑

- **现象**：内容质量不差，却几乎不被引用。→ **原因**：正文由客户端渲染，抓取器拿到的 HTML 里没有可摘段落。→ **对策**：首屏与正文改为构建期渲染，交互与增量数据留给客户端。
- **现象**：被引用时断章取义，结论说反了。→ **原因**：结论藏在段落中后部，前置铺垫被单独切走。→ **对策**：每节首句写完整结论，主语和条件一起写清。
- **现象**：同一指标在不同页面数字不一致，读者来信质疑。→ **原因**：数据散落在多处手写文案里，更新时漏改。→ **对策**：数据集中到一处配置，页面与 JSON-LD 都从同一处读取。
