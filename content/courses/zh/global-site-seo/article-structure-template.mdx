写作最耗时的不是写，是想结构：先铺垫背景，再讲原理，最后才给结论——读者在第一屏没拿到任何可用信息就走了。博客时代的「娓娓道来」在搜索场景里等于把答案藏在第三屏，而决定排名的恰恰是那些直接回答问题的页面。

骨架的价值在于：它把「想结构」变成「填槽位」。填不满的槽会暴露内容不足，而不是让你用废话凑字数。

## 五段骨架：结论 → 适用前提 → 步骤 → 证据 → 下一步

| 段位 | 写什么 | 长度占比 | 判断标准 |
| :--- | :--- | :--- | :--- |
| 结论块 | 直接回答标题里的问题，一到三句 | 10% | 读者只读这一段也能用 |
| 适用前提 | 版本、环境、前提条件、不适用场景 | 10% | 说清「什么情况下不适用」 |
| 主体步骤 | 可跟做的操作或判断步骤，一步一节 | 55% | 每节有一个可复制产物 |
| 证据 | 表格、命令输出、截图、真实数据 | 15% | 每个结论有对应证据 |
| 下一步 | 一个 CTA，不是三个 | 10% | 只留一个 |

商业调查型文章把「适用前提」换成「选型标准」，把「步骤」换成「对比表 + 适用人群」；信息型文章则把「证据」提前，紧跟结论块，因为读者最先怀疑的是「凭什么」。

## 可直接粘贴的 MDX 骨架

本站正文是 MDX，骨架可以直接写成文件头：

```mdx
## 一句话结论

<结论，1–3 句，包含数字或明确判断>

## 适用前提

- 环境 / 版本：
- 成立条件：
- 不适用：

## 步骤一：<动作>

<为什么这么做> 、<怎么做>

## 对照表

| 方案 | 成本 | 适用 | 风险 |
| :--- | :--- | :--- | :--- |

## 常见错误

- 现象 → 原因 → 对策

## 下一步

<唯一 CTA>
```

标题本身也要守规矩：包含目标关键词的自然表达、不堆叠两个意图、长度控制在一行内。标题里出现 `2026` 或具体版本号时，必须在正文同步维护，否则一年后就是过期内容。

## 每个小节只承担一件事

一节里同时讲「原理 + 操作 + 坑」，读者会跳过整节。拆法：原理一节（为什么），操作一节（怎么做），坑单独放进文末清单。判断标准是小节标题能不能被当成目录条目读——如果标题写成「一些细节」，说明这一节没有单一主题。

首屏尤其要克制：第一屏只放结论块和适用前提，不要放目录、不要放作者介绍、不要放订阅弹窗。静态导出站点没有服务端个性化，首屏给什么，爬虫和用户就先看到什么。

## 结构要跟页面层对齐

`app/**/page.mdx` 里的文档页适合「结论 → 步骤 → 参考」；`content/courses/zh/**` 的课时适合「痛点 → 3–5 个小节 → 落地动作 → 常见坑」。同一套骨架在不同层要换顺序，而不是换内容。课程页有 `objectives` 字段，正文的每节最好能对应回一条 objectives——对不上就说明这一节是凑的。

结构化数据也在读结构：Article 的 `headline`、`description` 与正文首段不一致时，摘录会打架。写完先自查首段是否独立成义。

## 落地动作

1. 把上面的骨架存成编辑器 snippet（VS Code 的 `mdx.json` 用户代码片段），新建文章时一键展开，先填标题和结论块。
2. 挑一篇现有文章，按骨架重排：把结论移到第一屏，删掉与结论无关的铺垫，把散落的数字收进一张表。
3. 发布前跑一遍检查清单：结论在第一屏、每节一个主题、至少一个可复制产物、只有一个 CTA、标题与首段说同一件事。

## 常见坑

- **现象**：文章长度够，跳出率高、停留短。→ **原因**：结论在第三屏，前两屏是行业背景。→ **对策**：把背景压到两句，结论提到首段，背景改成「适用前提」里的一个条件。
- **现象**：读者照着做卡在某一步。→ **原因**：步骤假设了读者已有环境，省略了前置条件。→ **对策**：每步补「在什么目录 / 什么版本下执行」，把前置条件单独成节。
- **现象**：同一篇文章里挂了三个 CTA，转化反而更差。→ **原因**：读者在决策点被分散。→ **对策**：只保留与本文意图匹配的一个 CTA，其余改成文字内链。
