每周只有几十个访问者的定价页做 A/B，得到的只是噪声；在取消流程里加三道确认，换来的是退款和差评。转化优化的工作量不在实验，而在于分清哪些问题不需要实验，哪些「挽留」只是在添堵。

## 先修确定性错误，再做实验

定价页上有一批问题不需要数据就能判定是错的，逐条核对：价格单位没写清，`$19` 旁边不写每月还是每年，用户会按最有利的方式理解；结算币种与税费位置没说明，Stripe 结账页按账单地址追加税费时，定价页写「含税」就对不上；退款政策只放在页脚，等于没写。

措辞也要一致：列表页写「了解更多」而定价页写「立即购买」，会让人怀疑还有一层；移动端对比表横向溢出，第三列看不见等于没有。

这些改动只要半天，收益比任何实验都确定：先改完再看数据。

## 单人做 A/B 的现实

做实验前先算账：在线样本量计算器输入当前转化率与想检测的最小差异，看每个变体需要多少转化。若算出要跑几个月，就不做 A/B，直接改成最有把握的版本。

值得测的变量很少，一次一个：两层还是三层、年付怎么展示、主 CTA 措辞。

实现方式有两种。自己分流：在边缘或服务端按 cookie 分配变体，曝光与事件可控，但要求运行时在首次渲染前读写 cookie。两套 Checkout 链接：最省事，但同一用户可能看到两个价，来源也会混。

停手条件必须事前写下：样本量多少、最晚哪天结束。中途反复看结果是最常见的自欺：看到「显著」就停，本质是在挑数据。

## 取消流程：给选择，不设障碍

顺序固定：先问一次原因（一个下拉），再给一个匹配的选项，最后始终保留「仍然取消」。

四个选项按实现成本排序：暂停收款（用 `pause_collection` 暂停扣款、保留订阅与历史，对应「暂时不用」）；降级到低价档（换一个 price，对应「用量或预算不够」）；延长当期账期（对应「首次取消、没用满周期」）；一次性折扣（只给明确表达价格异议的人，且只给一次）。

反模式很明确：隐藏取消入口、要求联系客服、要求打电话。短期能压住流失率，代价是退款率与拒付率上升，而 Stripe 都记录在案。

| 挽留手段 | 触发条件 | 实现位置 | 成本 | 对留存的作用 | 风险 |
| --- | --- | --- | --- | --- | --- |
| 暂停收款 | 季节性、暂时不用 | `pause_collection` | 低 | 保留订阅关系与数据 | 到期不会自动恢复 |
| 降级 | 用量或预算不足 | 换 price | 中 | 降低直接流失 | 功能落差导致二次流失 |
| 延长账期 | 首次取消、未用满周期 | 延长当期或发优惠码 | 低 | 争取一次真实使用 | 被反复使用 |
| 一次性折扣 | 明确的价格异议 | 创建 coupon | 低 | 短期挽回 | 训练用户等折扣 |
| 直接取消 | 低客单或明确不满 | 立即取消 | 最低 | 无 | 无 |

```ts
// 默认走「到期取消」：保留用户已付费的当期权益
await stripe.subscriptions.update(subscriptionId, {
  cancel_at_period_end: true,
});

// 暂时不用：暂停收款，订阅与历史都保留；恢复需要显式调用
await stripe.subscriptions.update(subscriptionId, {
  pause_collection: { behavior: "void" },
});

// 明确的价格异议：只给一次，避免训练出等折扣的习惯
const coupon = await stripe.coupons.create({ percent_off: 20, duration: "once" });
```

页面上必须写清服务到哪天结束。用户点了「取消」仍被扣一次款，多数不是系统错，是文案没说清。

## 什么时候不做挽留

客单价低、退款成本高的产品，直接退：一封邮件的客服成本可能超过一个月利润。

付费用户不到一百个，手动回每一封取消邮件：得到的原因比任何流程都具体，还能直接改产品。

原因明确是「产品没解决我的问题」，挽留只是把退款推迟一个月，还多一次差评。

## 落地动作

1. 按上面的摩擦点逐条核对定价页，今天先改完不需要实验的部分。
2. 在 GA4 建 `view_pricing → begin_checkout → purchase` 漏斗，`begin_checkout` 已有埋点，补前两个即可。
3. 选定一个变量，写下样本量与停手日再上线；边缘分流与两套 Payment Link 不要混用。
4. 取消端点默认返回 `cancel_at_period_end: true`，同时提供暂停选项，并在响应里带回本期结束时间。
5. 前一百个取消逐条记录下拉选项，按周汇总——这是改产品而非改文案的依据。

## 常见坑

- **现象**：A/B 跑了三周没有结论 → **原因**：样本不足，中途又多次看结果 → **对策**：上线前写死样本量与停手日，期间只看错误日志。
- **现象**：用户点了取消，下个月还在扣款 → **原因**：`cancel_at_period_end` 被当成立即取消，页面上也没写到期日 → **对策**：确认页显示「服务至 X 年 X 月 X 日」，邮件里再重复一次。
- **现象**：暂停的用户半年后仍在暂停状态，以为已注销 → **原因**：`pause_collection` 不会自动恢复 → **对策**：记录恢复日，提前一周提醒，并给一键恢复。
