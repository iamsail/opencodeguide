第一个付费用户写信说「付了钱没收到邮件」时，你能不能在五分钟内答出三件事：他到底付了没有、邮件发了没有、断在哪一步。可观测性是为这三个问题付的钱，不是为一块好看的仪表盘。

## 先定要回答的问题，再决定装什么

三个问题：谁受影响（哪条订单、哪个用户、哪个事件）、从什么时候开始（是不是某次发布之后）、是不是我这次改动造成的（按版本区分）。

答案定完，配置范围就定了：要能按订单或事件 id 检索日志，日志里要有版本或部署标识，错误要能按版本对比。配不上的东西先别配；还没人付款的阶段接一整套 APM，只会多一个要维护的面板。

## 日志：一行一个 JSON，带 requestId

平台日志面板大多只能按字符串过滤。多行打印的日志拼不回一次请求，`console.log(error)` 也只留下一个没有上下文的字符串。

```ts
type LogLine = {
  level: "info" | "error";
  event: string;            // 稳定事件名，能直接 group by
  requestId: string;        // 同一次请求的所有日志共用
  orderId?: string;
  durationMs?: number;
  err?: { name: string; message: string; stack?: string };
};

export function log(line: LogLine) {
  console.log(JSON.stringify({ ts: new Date().toISOString(), ...line }));
}
```

约定三条：事件名用稳定的字符串常量，别把它拼进自由文本；同一次请求复用同一个 `requestId`；错误日志打对象而不是字符串。仓库的 course-delivery Worker 在 Webhook 入口就把事件 id 与 session id 记下来，所以「这条事件处理过几次」可以直接从日志回答，不必猜。

## 事实与漏斗要分开，别拿埋点对账

订单是事实，埋点是参考。GA4 这类客户端事件在跳转前可能没发出去，也可能被拦截器丢掉，用它算收入一定对不上。

仓库的分工值得照搬：`begin_checkout` 只给 GA4 做漏斗，付款结果落在订单表里，两边靠 `client_reference_id`（`slug:plan`）对齐。想验证交付链路，查的是 `email_status` 这类字段，不是事件数。

| 需求 | 最小方案 | 换掉的信号 | 代价 |
| --- | --- | --- | --- |
| 崩溃与异常堆栈 | 平台错误日志，或 Sentry | 要按版本对比、要看 source map | 按事件量计费，必须过滤 PII |
| 请求日志 | 平台日志面板 + 一行 JSON | 要跨服务检索、要长期留存 | 免费留存期短，久了要外导 |
| 业务漏斗 | GA4 客户端事件 | 要和订单对账 | 会被拦截器丢弃，不能当事实 |
| 支付与交付异常 | Stripe Dashboard + 订单表查询 | 需要多人值班、要自动告警 | 告警查询要自己写 |
| 用量计量 | 自己的 usage 表 | 计费改为按用量 | 每条请求多一次写入 |

用量计量和限流是模块 3 的内容，这里只要求：每次调用写一行 `user_id + 日期 + 计数`，别等到要收费时才发现没数据。

## 只留三条告警

告警多了等于没有告警。一个人维护，三条足够：支付成功率低于最近两周的常态、Webhook 返回 5xx、出现发信失败的订单。

第三条可以直接用仓库 README 里的查询：`select ... from orders where email_status in ('failed','needs_manual_delivery')`。它比任何指标都直接，因为它数的就是「有人付了钱但没拿到东西」。

什么时候不用做：还没有付费用户时，只配错误追踪加一条支付失败告警，其余等有量再说。

## 落地动作

1. 建 `lib/log.ts`，只导出上面那个 `log()`，禁止业务代码直接用 `console.log` 打调试信息。
2. 在 Webhook 入口生成一个 `requestId`，把 `event.type`、`event.id`、`session.id` 各打一行 info；失败分支用同一 `requestId` 打 error。
3. 配三条告警，收件人写自己的邮箱；每条都在测试环境手动触发一次，确认能收到。

## 常见坑

- **现象**：日志里全是同一句话，看不出是哪个订单出的错。 → **原因**：只打了 `error.message`，丢了事件名与请求上下文。 → **对策**：改成打对象，强制带 `event` 与 `requestId`，把这条写进代码评审清单。
- **现象**：错误追踪的账单因为一次故障暴涨。 → **原因**：同一个错误在循环里每条请求都上报。 → **对策**：设采样率，并对相同特征（同一堆栈位置）的错误去重，只在首次与恢复时通知。
- **现象**：漏斗显示下单很多，Stripe 里却没几单。 → **原因**：客户端事件在跳转前没发出去，或被广告拦截器丢弃。 → **对策**：把订单表当作唯一事实来源，漏斗只用来定位流失步骤，不用来汇报业绩。
