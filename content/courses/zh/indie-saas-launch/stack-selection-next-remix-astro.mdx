框架选错的账单不会在第一个月寄到。它出现在你想加一个「登录后观看」的会员中心、发现整站托管模型要换一遍的那天。选型要回答的不是哪个框架更好，而是服务端代码将来放在哪、换掉它要付多少。

## 先确定服务端边界，再挑框架

三个问题能定掉大部分结论：页面要登录吗？收款要不要接 Webhook？有没有页面必须读 cookie 或数据库才能出 HTML？

三个都是「否」，你面对的就是一个内容站加一次支付跳转，静态导出足够。仓库的课程站走的就是这条路：`output: 'export'` 的纯静态导出，函数调用为 0，收款交给 Stripe 托管的结账页，付款后的交付放在独立的 Cloudflare Worker 里。静态站与运行时被拆成两个部署单元，任何一边都能单独换掉。

只要有一个页面必须读 cookie 才能渲染，静态导出就出局，你必须选一个带服务端运行时或边缘函数的框架。

```js title="next.config.mjs"
/** @type {import('next').NextConfig} */
const nextConfig = {
  output: "export",              // 构建产物是纯静态文件，放在 out/
  trailingSlash: true,           // 导出后 /courses 与 /courses/ 不再多一次跳转
  images: { unoptimized: true }, // 静态导出下没有图片优化服务
};

export default nextConfig;
```

## 三种渲染模型，成本落在不同地方

| 维度 | Next.js | Remix | Astro |
| --- | --- | --- | --- |
| 默认渲染 | 服务端优先，可逐路由退回静态 | 服务端渲染，表单渐进增强 | 构建期出静态 HTML，交互靠 islands |
| 服务端代码位置 | Route Handler、Server Action | loader、action | API 路由或 SSR 模式 |
| 纯静态导出 | 支持，但动态能力受限 | 需自己搭一套 | 默认就是 |
| 登录后的应用页 | 原生支持 | 原生支持 | 需额外渲染模式，或拆成第二个应用 |
| 迁移到会员中心的代价 | 低，同框架内加服务端 | 低 | 高，等于换框架 |
| 一个人上手成本 | 中，概念多 | 中，心智更接近 Web 标准 | 低，但仅限内容站 |

Astro 那一栏不是缺陷而是取向：它以内容页为中心，交互靠局部的岛。整页级的应用状态（登录后的仪表盘）没有一等支持，硬塞会变成「一页里放三个岛，岛之间还要通信」。

## 迁移代价藏在组件层

Next.js 与 Remix 都是 React，页面组件、hooks、样式基本能搬；搬不动的是数据获取方式与路由约定，这部分工程量通常大于页面的视觉部分。Astro 反过来：内容页几乎零成本，交互组件要重写。

所以判断标准可以收成一句：未来 12 个月，登录后的应用页面会不会多于内容页？会，就别从 Astro 起步；不会，Astro 的构建速度和干净输出是真的省事。

## 最小可行版本，以及什么时候不用选

一个人做，最小版本是「静态站 + Stripe Payment Link + 一个只处理 Webhook 的 Worker」。仓库的 course-delivery 就是这个形态，静态站不用为了收钱改架构，Webhook 与邮件也不占站点托管。

什么时候不用做选型：当你的交付物只是一封邮件里的观看链接和仓库邀请，登录根本不存在。这时选你最熟的那个框架，把时间花在落地页和定价上。选型讨论在「需要服务端」之前都是伪问题。

## 落地动作

1. 在仓库根建 `docs/stack.md`，只写三行：需要登录的页面数、需要 Webhook 的收款、需要服务端渲染的页面数。这三个数字就是选型的输入。
2. 用官方脚手架建空项目，把上面那段 `next.config.mjs` 写进去，跑 `npm run build`，确认产物目录里有 `out/index.html`。构建能通过，说明静态这条路可行。
3. 在 `docs/stack.md` 末尾写一条迁移触发条件，例如「出现第一个必须读 cookie 的页面时，把该路由改为部署到 Worker，主站保持静态」。

## 常见坑

- **现象**：本地 `npm run dev` 一切正常，`npm run build` 报错说某个页面用了不支持导出的动态 API。 → **原因**：`output: 'export'` 下无法在构建期确定的路由里读 cookie 或请求头。 → **对策**：把这类页面移出主站，或改用带服务端运行时的托管，别在静态导出里打补丁。
- **现象**：为了「以后可能做会员中心」提前上了 SSR 和数据库，两个月过去登录功能还没写。 → **原因**：把可选项当成了必需项，成本先付、收益没到。 → **对策**：先用 Payment Link 上线，收到第一笔钱之后再引入服务端，仓库那两个阶段的边界就是现成模板。
- **现象**：Astro 站上想加一个需要登录的仪表盘，越写越别扭。 → **原因**：Astro 的 islands 是为局部交互设计的，不适合整页级应用状态。 → **对策**：仪表盘独立成子域，用 React 框架单独部署，两个站共享同一份登录态与数据库。
