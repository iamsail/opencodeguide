合规最贵的不是做不到，是「按网上的清单全做一遍」：cookie 同意平台、政策生成器、数据地图工具各装一套，真来了一个删除请求，还是没人能跑出这条 SQL。合规的最小单位不是工具，是三个能当场执行的流程。

## 先判断义务是否落在你身上

GDPR 没有营收门槛。只要向欧盟境内的人提供商品或服务，哪怕免费，就在适用范围内；「我才几百个用户」不是抗辩理由。CCPA / CPRA 则有营收与数据量门槛，单人 SaaS 多数达不到，但门槛每年要重估，且加州居民来信仍然要回。

| 义务 | GDPR | CCPA / CPRA | 一个人的最小动作 |
| :--- | :--- | :--- | :--- |
| 告知收集了什么 | 必须有合法基础 | 必须在收集时告知 | 隐私政策写准，别抄模板 |
| 导出个人数据 | 一个月内响应 | 收到请求后响应 | 一条按邮箱聚合的 SQL |
| 删除 | 有权要求删除 | 有权要求删除 | 删账号并级联，交易记录匿名化 |
| 拒绝营销与追踪 | 反对权 | Do Not Sell / Share | 退订链接 + 拒绝分析脚本 |
| 处理者协议 | 必须签 DPA | 合同需含限制条款 | 各家平台的 DPA 直接接受 |

还有一条常被漏掉：不在欧盟设立、却处理欧盟用户数据时，可能要指定一名欧盟境内代表。做 B2C 且欧盟流量不低时先查清，别等收到问询。

| 合规路径 | 适用条件 | 覆盖到什么 | 代价 |
| :--- | :--- | :--- | :--- |
| 政策页加手工流程 | 客户以个人为主，请求每月个位数 | 告知、导出、删除 | 每次请求人工跑 SQL，量一上来就会拖过时限 |
| 引入同意管理平台 | 装了 GA4 之类需要事前同意的脚本 | 同意记录与撤回 | 订阅费；脚本要在同意后才加载，改造成本在代码侧 |
| 自建数据清单加处理记录 | 有企业客户，要答安全问卷、签 DPA | 处理活动记录、子处理者列表 | 一次投入几天，之后每加一个服务都要更新 |
| 暂不处理 | 还没有欧盟用户，也没企业客户 | 无 | 一旦有欧盟访客就已在范围内，补做时历史数据没有合法基础 |

## 字段表就是合规文档

不需要数据地图工具，把建表语句打印出来，逐列问三句：业务真需要吗，能匿名化吗，留多久。多数单人产品在这几列上翻车：生日只为了发祝福、手机号收了却从不发短信、完整 IP 在日志里躺两年。

保留期必须写成策略并有人执行：订单与发票按当地财务留存要求保存，应用日志按排查需要保存，营销联系人按活跃度清理。没有保留期的意思是「永久保存」，而永久保存既是风险也是成本。

## 三条流程：导出、删除、拒绝

导出要覆盖所有表，先列出哪些表里有邮箱或用户 ID。请求者不懂你的表结构，但你要给可读的 JSON，不是一堆外键。

删除分两类：账号与附属数据真删，交易记录匿名化保留——税务留存义务优先于删除权，Stripe 侧的交易记录也删不掉。删除还要同步给处理方：邮件服务的联系人、分析工具的用户 ID。

```sql
-- 导出：一个邮箱在系统里的全部记录，拼成可直接回给用户的 JSON
select json_build_object(
  'exported_at', now(),
  'account', (
    select row_to_json(u) from (
      select id, email, created_at, last_login_at from users where email = $1
    ) u
  ),
  'orders', (
    select coalesce(json_agg(o), '[]'::json) from (
      select id, amount_cents, currency, status, created_at
      from orders where email = $1
    ) o
  )
);

-- 删除：交易记录匿名化保留，账号及其级联数据真删
update orders
   set email = 'deleted+' || id::text || '@invalid.local',
       ip_address = null,
       deleted_at = now()
 where email = $1;

delete from users where email = $1;  -- sessions / api_keys 依赖 on delete cascade
```

拒绝要落到具体开关：退订链接、分析脚本的拒绝状态、浏览器发来的 Global Privacy Control 信号。GPC 是个请求头，读到它就该主动关掉非必要追踪。

## 同意只在有非必要脚本时才成为问题

只放登录态与 CSRF 这类必要 cookie，不需要横幅。装了需要事前同意的分析或广告脚本，才需要同意管理，而且同意前的页面里不能出现该脚本——先加载再弹窗，等于没有同意。

| 分析方案 | 需要同意横幅吗 | 适用条件 | 代价 |
| :--- | :--- | :--- | :--- |
| 不装分析，只看支付后台与搜索后台 | 不需要 | 早期，只判断有没有人买 | 没有行为数据，页面问题靠访谈 |
| 自托管分析（Plausible、Umami 一类） | 通常不需要 | 想知道 PV 与来源 | 多一个服务要维护，事件口径要自己定 |
| GA4 加同意管理 | 需要，且要能撤回 | 要接广告投放与转化归因 | 同意率决定数据完整度，代码要改成延迟加载 |

## 落地动作

1. 把全部建表语句导出到 `docs/data-inventory.md`，每列标注「用途 / 保留期 / 能否匿名化」，删掉三列以上再上线。
2. 把上面的导出与删除 SQL 存成 `scripts/gdpr.sql`，用两个参数分开发布，删除语句加 `--dry-run` 先跑一次 `select count(*)`。
3. 加一条定时清理：日志超过保留期就删，订单不动。

```bash
# 保留期执行：应用日志只留 30 天，先看要删多少行再删
psql "$DATABASE_URL" -c "select count(*) from app_logs where created_at < now() - interval '30 days';"
psql "$DATABASE_URL" -c "delete from app_logs where created_at < now() - interval '30 days';"
```

4. 补上处理者与跨境传输依据（标准合同条款或等效机制），从各平台信任中心接受 DPA——不需要谈判，只要有人点。

订单还是个位数时，只做三件事：政策页写准、删账号的 SQL 跑通、日志设保留期。同意管理平台、代表指定、处理活动记录，等出现第一个欧盟企业客户或第一次安全问卷再补。

## 常见坑

- **现象**：用户要求删除，跑完 `delete from users` 后对方仍收到营销邮件 → **原因**：邮箱还留在邮件服务商的联系人表与分析工具里，删除只做了主库 → **对策**：把「删除」写成清单式流程，每清理一个系统就打勾，处理方侧的删除用其 API 或后台完成并留下记录。
- **现象**：欧盟用户投诉「没同意就被追踪」→ **原因**：分析脚本写在 `<head>` 里同步加载，横幅只是装饰 → **对策**：脚本按同意状态动态注入，拒绝时完全不请求，并在隐私政策里说明撤回方式。
- **现象**：为了合规把订单表也清了，年底对不上账 → **原因**：把删除权理解成「所有数据都删」→ **对策**：区分个人数据与交易记录，账号数据删净、交易记录匿名化保留，并在回复用户时说明保留范围与依据。
