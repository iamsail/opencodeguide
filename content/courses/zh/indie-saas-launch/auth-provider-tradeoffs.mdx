登录本身两天能写完，贵的是它后面两件事：用户表在谁手里，以及你想换掉它时能不能把用户带走。选认证方案时，API 好不好用排在第三位。

## 真正的差别是用户表归谁

Clerk 把用户托管在自己那边，SDK 给你现成的组件和会话，你的库里通常只存它的 user id 和邮箱。Supabase Auth 把用户放在你自己的 Postgres 的 `auth` schema 里，可以直接和业务表 join。Auth.js 是一个库加一组适配器，用户表由你自己定义，第三方 provider 只是入口。

这条差别会决定三件事：能不能按邮箱直接 join 订单、导出用户时要不要另写脚本、出问题时能不能自己查库。技术清单上的功能对比，在这里几乎不起作用。

## 按 MAU 计费的账要提前算

托管认证按活跃用户计费，具体单价以官网当期价目表为准，这里不给数字，给算法：拿价目表算出「第 1 千 MAU 与第 1 万 MAU 时的月费」，再除以对应的月收入，看这个比例随规模是升还是降。

如果边际成本随规模线性上涨，而客单价是一次性买断，那么用户越多、认证越贵，这条路会在某个点自己断掉。这不是说不能用托管方案，而是说要提前写下触发条件：当认证月费超过某个比例的收入时，开始准备迁移。比例自己定，写进文档，别靠感觉。

## 迁移风险具体长什么样

能带走的：邮箱、创建时间、外部 provider 的绑定关系（多数方案可导出）。要重建的：密码哈希格式（导出后需按目标方案重新写入）、MFA 注册状态、活跃会话。

降低风险的办法不在迁移那一刻，在建表那一刻：业务表只存自己的 `user_id` 和 `email`，不要把服务商的用户对象整个序列化进去。这样迁移只影响认证层，业务表一行不用改。

```sql
-- 登录成功后把历史订单合并成权益：邮箱是唯一的连接键
insert into entitlements (email, course_slug, plan_id, order_id)
select o.email, o.course_slug, o.plan_id, o.id
from orders o
where lower(o.email) = lower($1)
  and o.status = 'paid'
on conflict (email, course_slug) do update
  set order_id   = excluded.order_id,
      revoked_at = null;
```

这段的前提是「先付款、后注册」：Stripe 一定收到邮箱，用户注册时用邮箱匹配历史订单，权益才不会丢。任何认证方案都必须能给出一个可信的邮箱，否则这条链路补不上。

| 维度 | Auth.js | Clerk | Supabase Auth |
| --- | --- | --- | --- |
| 用户表位置 | 你的库，schema 自己定 | 服务商托管 | 你的 Postgres 的 auth schema |
| 登录 UI | 自建，或用生态组件 | 预置组件，改造受其 API 限制 | 有预置组件，也可自建 |
| 计费 | 库本身免费，成本是你的维护时间 | 按 MAU，以官网当期为准 | 随 Supabase 套餐，按 MAU 计 |
| 与订单表 join | 直接 join 自己的表 | 需额外存邮箱，用其 user id 关联 | 可直接 join |
| 退出成本 | 低，数据本来就在你手里 | 中高，用户与 MFA 都要重建 | 中，同库但要脱离其 SDK |
| 适合条件 | 想完全掌控用户模型 | 想两天上线、接受托管 | 已用 Supabase 做库 |

## 先不做的条件

如果交付物是观看链接、模板仓库邀请和社群邀请，邮件就够了。仓库的 course-delivery Worker 就是这么做的：付款后遍历订单发信，全程没有登录。这一版能撑到几百单，运维成本接近零。

什么时候必须上登录：需要按人回收权限（退款后立即失效）、需要学习进度、需要用户自助换绑邮箱。这三件事任一出现，邮件交付就开始漏，那时再上认证。

## 落地动作

1. 在 `docs/auth.md` 写三行：交付物是否需要登录才能拿到、预计 12 个月的 MAU、退出时必须带走的字段。第三行决定你的业务表长什么样。
2. 不管选哪家，业务表只加 `user_id` 与 `email` 两列，绝不存服务商返回的整个用户对象。
3. 建 `entitlements` 表并保留 `(email, course_slug)` 唯一约束，用上面那段 SQL 拿一条历史测试订单跑一次，确认权益能被正确合并。

## 常见坑

- **现象**：用户付了钱，登录后看不到课。 → **原因**：结账用了一个邮箱、注册用了另一个（大小写不同或用了别名地址）。 → **对策**：比较时统一 `lower(email)`，结账页预填邮箱，注册后触发一次历史订单合并。
- **现象**：从托管方案迁走时，开了 MFA 的用户全部要重新绑定。 → **原因**：MFA 的密钥与恢复码通常不可导出。 → **对策**：把「MFA 用户需重新注册验证器」写进迁移预案，或等用户规模稳定后再开 MFA。
- **现象**：每个页面各写一段会话判断，越写越不一致。 → **原因**：没有单一入口，鉴权逻辑散落在路由里。 → **对策**：只留一个 `requireUser()`，业务代码只读它返回的 `email` 与 `user_id`，换方案时只改这一个函数。
