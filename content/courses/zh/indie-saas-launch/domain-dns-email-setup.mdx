域名通常拖到上线前一天才买，然后一次踩三个坑：站点解析生效了，收据邮件却进了垃圾箱；发信和官网共用主域，一次群发把信誉打穿；DMARC 直接上 `p=reject`，结果自己的开通邮件先被拒。域名、解析、发信身份是三件事，只是恰好写在同一个 DNS 文件里。

## 站点域名与发信域名是两套东西

买域名只有一个决策：注册商放哪，它只影响续费与转移难度。真正影响后面半年的是另外两件事：DNS 托管给谁、发信域名用主域还是子域。

默认把 `example.com` 留给官网和人工邮箱，把事务邮件放到 `send.example.com`。理由是信誉隔离：收据、批量通知、营销邮件的退信率不同，混在一个域上，一次群发失误会让收据一起被降权。代价是多一套记录，DMARC 要按子域单独设策略。

只有长期只发事务邮件、且量很小，才值得把发信放主域：少一层配置，也没有隔离带；开始发 newsletter 再迁移，就要重做验证。

解析托管同理，自带的够用就别迁。用 Cloudflare 时记住代理只作用于 A、AAAA 与 CNAME：发信服务商让你加的验证记录如果是 CNAME，别开橙云，否则验证会莫名失败。

## SPF 粗筛、DKIM 签名、DMARC 定规矩

SPF 是一条以 `v=spf1` 开头的 TXT，声明哪些服务器可以代表这个域发信。它按发信 IP 匹配，邮件被转发后源 IP 变了就失效，只能算粗筛。

DKIM 用私钥签名、公钥放在 DNS 的 TXT 里，选择器名由服务商给（常见形如 `resend._domainkey`）。它验证的是邮件在传输途中是否被改过，能扛住转发，是三者里最可靠的一环。

DMARC 放在 `_dmarc` 下，规定「SPF 和 DKIM 都没过时怎么办」，并用 `rua=` 指定接收聚合报告的邮箱；它自己不验证任何东西。

顺序不能反：DKIM 先验证通过，再上 DMARC。`p=reject` 会把签名缺失或对齐失败的邮件直接拒收，包括你自己的密码重置邮件。

## 先观察，再收紧，别一步到 reject

新域名没有发信信誉。第一周用 `p=none` 只收报告；确认收据、开通、密码重置三条链路都能进收件箱，再改 `p=quarantine`；稳定运行一段时间后才考虑 `p=reject`。

一步到 `p=reject` 的代价不是「可能出问题」，而是定位不到：报告没积累，收件方直接丢弃，连退信都没有。

同时确认 SPF 只有一条：两条 `v=spf1` 会被判无效，而「服务商让你加一条，你直接粘贴、旧的没删」是最常见的错法。

## 验证靠 dig，不靠「发一封试试」

配置完先看 DNS 再发信，能把「配置错」和「内容被判垃圾」两类问题分开：

```bash
# 站点解析：apex 与 www 都要指向托管平台
dig +short example.com A
dig +short www.example.com CNAME

# SPF：应当只有一条，且包含发信服务商
dig +short TXT example.com | grep spf1

# DKIM：选择器名以服务商后台显示为准，不要猜
dig +short TXT resend._domainkey.example.com

# DMARC：先从 p=none 开始
dig +short TXT _dmarc.example.com

# 换公共解析器交叉验证，排除本地缓存
dig @1.1.1.1 +short TXT _dmarc.example.com
```

返回空通常是名字查错：`_dmarc` 的下划线容易漏，DKIM 选择器常被写成 `default`。DNS 全部有值后再发真实邮件，Gmail、Outlook、QQ 邮箱各收一封——同一封信在这三家的判定经常不同。

## 决策表：发信域怎么放

发信域只有三种放法，差别在隔离程度与维护量。

| 布局 | 适用条件 | 代价 | 什么时候不用 |
| :--- | :--- | :--- | :--- |
| 子域发信 `send.example.com` | 有事务邮件，且计划发批量通知或 newsletter | 多一套记录；DMARC 与报告按子域分开维护 | 只发收据、发信量极小 |
| 主域发信 `example.com` | 单人产品，只有收据与密码重置 | 主域信誉与官网共用，没有隔离带 | 任何批量发信场景 |
| 独立域名 | 主域历史发信已被污染，或营销外包 | 品牌分裂，用户容易当钓鱼邮件 | 新域名、无历史包袱 |

## 落地动作

1. 确认域名 NS 指向哪家解析，结论写进 `docs/infra.md`。
2. 在发信服务商后台添加发信域名，把记录逐条粘进 DNS，粘完确认旧 SPF 已删。
3. 跑上面这几条 `dig`，输出贴进同一文件作为基线。
4. 第一周 DMARC 用 `p=none` 并填真实可收的 `rua`，收到报告后再决定是否收紧。
5. 发一封真实收据到三个邮箱，确认进收件箱而非垃圾箱。

## 常见坑

- **现象**：后台显示「已验证」，发信仍进垃圾箱 → **原因**：验证只覆盖域名归属，不覆盖 DMARC 对齐与内容信誉 → **对策**：先看 DMARC 报告的对齐结果，再查正文短链与图片比例。
- **现象**：加了新服务商的 SPF 后，原本正常的邮件开始失败 → **原因**：域上出现两条 `v=spf1`，整体失效 → **对策**：合并成一条，把新服务商的 `include` 追加进去。
- **现象**：DKIM 的 `dig` 一直返回空，服务商却说已生效 → **原因**：选择器名错，或多了一层 `send.` 前缀 → **对策**：按后台显示的全名逐字符对照，别凭记忆拼。
