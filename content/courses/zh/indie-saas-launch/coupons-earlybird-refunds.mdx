折扣出问题通常不在力度，而在它落在哪一层：做成新 Price，页面价格随之改变，到期只能靠人手停用；做成 Promotion Code，页面价格没变，客户截图与广告口径又对不上。

## 折扣落在 Price 上还是落在码上

Stripe 里只有两个地方放折扣：Price 定金额，Coupon 与 Promotion Code 定凭证。Coupon 定义减多少、减几次，Promotion Code 是客户在结账页输入的那串字符，一个 Coupon 可以挂多个码来区分渠道。

改价让所有流量同价，落地页与广告口径一致，归因干净；代价是金额不可改，调一次价就要新建 Price 和链接，旧链接还得留着看流量，忘了停用折扣就永久生效。发码让一个链接服务所有客群，代价是码会泄露到社群与比价站，必须配到期时间、次数上限、首单限制，而且结账页不会告诉你这个码来自哪个渠道。

两者还会叠加：早鸟 Price 的链接若仍允许输码，客户在折扣价上再打一次折。收入漏损多半出在这里，而不是折扣定得太狠。

| 做法 | 页面上公开的价格 | 适用条件 | 主要代价 |
| :--- | :--- | :--- | :--- |
| 新建 Price + 新 Payment Link | 就是折扣价 | 全员早鸟、公开预售、广告页需要价格一致 | 金额不可改；到期靠人工停用；每档价格一套链接 |
| Coupon + Promotion Code | 原价，折扣在结账页兑现 | 分社群、分渠道、老客户补偿、限时闪购 | 码会泄露，必须设到期与上限；渠道归因靠码本身 |
| 链接绑死 `discounts` 参数 | 自动减免，客户无需输码 | 某条链接专供一批人，如社群专属地址 | 无法区分谁用过；与优惠码输入框不能同时生效 |
| 不做折扣，只改文案 | 原价 | 还在验证定价，总量只有几十单 | 没有可回溯的折扣记录，事后算不清真实客单价 |

## 早鸟卖的是时间，不是折扣

早鸟真正承诺的是什么时候能看到什么，便宜只是包装。页面写「含全部 12 讲，10 月 31 日前更新完」，一旦延期，退款理由就成立，纠纷成本高于让出的折扣。把承诺写成可交付的粒度——已上线几讲、剩余几讲的时间窗——比写「完整课程」安全。

收口只有两个动作：给码设 `expires_at`，或停用链接。停用前必须确认没有渠道还在用它，链接一停，站点上的购买按钮就是死链。这个仓库把链接写进 `stripe-links.json` 并随仓库提交，改链接等于改配置再重新构建，不会出现后台与页面各说各话。

只维护得起一套价格时，就别做早鸟。定一个半年内不后悔的价格，用「上线后涨价」提供紧迫感，比养两套价格体系便宜。

## 退款按用掉多少分级，别只按天数

七天无理由是最好执行的规则：客服一句话，一次全额退款。代价是会被利用——买完立刻领仓库邀请、下完模板，第七天申请退款。按使用程度分级更贴近事实：未领取任何交付物全额退，已领仓库邀请退部分，约过 1:1 的只换不退。缺点是每单要人判断，规则必须写在退款页上，否则就是凭心情。

Stripe 侧只有全额与部分退款（`POST /v1/refunds` 带 `amount`，单位是分），退款原路返回，原交易手续费一般不退，以官网当期政策与所在地区为准，所以退款率是成本项。状态机判据要用累计值：`charge.refunded` 在部分退款时同样触发，是否退干净看 `charge.amount_refunded` 是否已不小于 `charge.amount`，只有全额才写 `revoked_at` 回收权限。

| 策略 | 适用条件 | 客户体验 | 你的代价 |
| :--- | :--- | :--- | :--- |
| 窗口内无条件全额 | 客单价低、笔数多、客服时间最紧 | 最好，几乎不产生工单 | 滥用风险最高，退款率虚高 |
| 按是否领取交付物分级 | 有可验证的交付动作，如仓库邀请、1:1 预约 | 需要解释，但能接受 | 每单人工判断，规则必须前置公示 |
| 只换不退 | 内容型产品、交付已发生 | 差，容易升级为拒付 | 拒付比退款贵，举证也麻烦 |
| 一律不退，靠条款挡 | 极低价或纯数字下载 | 最差 | 拒付率上升，Stripe 会盯账户 |

## 落地动作

1. 先建 Coupon，再建挂在它下面的 Promotion Code，把到期日与首单限制一次设全：

```bash
set -euo pipefail
: "${STRIPE_SECRET_KEY:?先导出测试模式密钥}"

# 1) Coupon：减 30%，只作用一次
COUPON_ID=$(curl -s https://api.stripe.com/v1/coupons \
  -u "$STRIPE_SECRET_KEY:" \
  -d percent_off=30 \
  -d duration=once \
  -d name="Early Bird 30" | jq -r .id)

# 2) Promotion Code：客户输入的那串字符，带到期与首单限制
#    到期时间用纯算术算，避免 macOS 与 Linux 的 date 参数差异
EXPIRES_AT=$(( $(date +%s) + 14 * 86400 ))
curl -s https://api.stripe.com/v1/promotion_codes \
  -u "$STRIPE_SECRET_KEY:" \
  -d coupon="$COUPON_ID" \
  -d code=EARLYBIRD30 \
  -d "expires_at=$EXPIRES_AT" \
  -d "restrictions[first_time_transaction]=true" | jq '{code, active, expires_at}'
```

2. 打开对应 Payment Link，确认 `allow_promotion_codes` 为真，用 `4242 4242 4242 4242` 走一遍，验证码生效、过期码报错。
3. 订单表加 `status`、`refunded_at`、`revoked_at` 三列，把退款分级按「领取了什么」写成退款页上的四条规则。
4. 在 `stripe-links.json` 给早鸟链接记一行注释（到期日与停用动作），到期当天停用或换链。

## 常见坑

- **现象**：客户反馈码输不进去 → **原因**：链接没开 `allow_promotion_codes`，或该结账页已绑固定减免，两者不能同时生效 → **对策**：按 Dashboard 的链接设置确认后重建并实测一次，不要用客服手工退款补折扣。
- **现象**：早鸟截止后仍有折扣订单进来 → **原因**：旧链接还挂在落地页、邮件模板、社群公告里，Price 不会自己涨价 → **对策**：先 `grep -rn "buy.stripe.com" content/` 找出全部引用，替换并重新构建，再停用旧链接。
- **现象**：部分退款后用户权限被收回，客诉升级 → **原因**：用事件里本次退款额判断是否全额 → **对策**：改用 `amount_refunded >= amount` 判定，部分退款保留访问，只在全额时写 `revoked_at`。
