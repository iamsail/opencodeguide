测试模式点一次成功卡，就认为支付接好了。上线后第一个问题往往不是「付不了款」，而是「付了款没收到东西」；第二个是「退了款还能继续看」。测试模式只验证最短那条路径，这两件事它都不会暴露。

演练要证明的不是能收款，而是每条异常路径都有确定的归宿。

## 四条路径，一条都不能省

成功路径验证的是金额、币种、商品名三项与页面一致，以及支付完成后落到哪个页面。

3DS 路径验证的是跳转链路没断：有些实现会在验证回来后丢掉会话参数，用户卡在空白页。

失败路径验证的是卡被拒后用户停在哪里。理想结果是停在支付平台并看到明确错误，而不是回到你的站点显示「支付成功」。

退款与拒付路径验证钱和权限能否一起回退。退款是你主动操作，拒付（chargeback）由用户向银行发起，两者事件不同，处理逻辑常常只写了一半。

## 用测试卡把结果跑出来

| 场景 | 卡号 | 预期结果 |
| :--- | :--- | :--- |
| 成功支付 | 4242 4242 4242 4242 | 跳回感谢页，订单摘要正确 |
| 需要 3DS 验证 | 4000 0025 0000 3155 | 弹出验证，通过后落到感谢页 |
| 余额不足 | 4000 0000 0000 9995 | 结账页报错，用户留在支付页面 |
| 触发拒付流程 | 4000 0000 0000 0259 | 后台可走争议流程，权益应被标记 |

这四张卡只对测试模式有效。正式模式用真实卡，所以最后一轮必须换成一笔真实小额订单——这也是验收清单里唯一无法用自动化替代的一项。

## 测试模式与正式模式差的不是密钥前缀

四个地方是两套：密钥（`sk_test_` 与 `sk_live_`）、webhook 端点、支付链接、邮件里的跳转域名。任何一处只配了测试版，上线后就是静默失败。

最容易漏的是 webhook。测试模式跑通后，正式模式的事件投递到另一个地址，如果那个地址没配或没部署，订单就永远不会入库，而支付本身完全成功——用户付了钱，你什么都不知道。

补救办法：正式模式小额单付完后，去后台事件列表看投递结果。状态成功才算链路通，只看支付成功不够。

## 幂等与重放：把设计变成两条断言

事件可能重复到达，这是投递语义决定的，不是异常。处理函数怎么设计属于实现，演练要做的是把它变成可执行的断言，在上线前跑出空结果。

```bash
# 本地转发事件，确认签名校验通过
stripe listen --forward-to localhost:3000/api/stripe/webhook

# 触发一条成功事件，观察订单表是否只写入一条
stripe trigger checkout.session.completed

# 盯住投递失败的事件
stripe logs tail
```

```sql
-- 断言 1：一个 checkout session 只能对应一条订单（字段名按你的表调整）
select stripe_session_id, count(*) as n
from orders
group by stripe_session_id
having count(*) > 1;

-- 断言 2：已付款却没有权益，就是交付缺口
select o.id, o.email
from orders o
left join entitlements e on e.email = o.email
where o.status = 'paid' and e.id is null;
```

第二条更值得盯：重复订单只是账目难看，交付缺口会让用户直接要求退款。最快的验证方式是在后台事件详情里重发一次真实事件，再看这两条查询。

## 决策表：哪些演练项可以砍

演练全部做完要半天。真正可以省的只有一类：路径根本不存在。

| 演练项 | 最小做法 | 什么时候可以不做 | 不做的代价 |
| :--- | :--- | :--- | :--- |
| 成功支付 | 4242 卡走一遍，核对三项 | 不可省 | 收错钱、跳错页 |
| 3DS | 3155 卡走一遍 | 客群里欧洲卡占比极低 | 部分地区用户付不了款 |
| 支付失败 | 9995 卡走一遍 | 不可省 | 不知道失败后用户停在哪 |
| 退款 | 后台全额退一笔 | 不可省 | 退了钱权益没回收 |
| 收据邮件 | 三个邮箱各收一封 | 不可省 | 用户付款后拿不到东西 |
| webhook 重放 | 后台重发一次事件 | 只有静态页与托管结账页、无服务端 | 引入服务端后才暴露重复发货 |

最后一行能合理推迟：只有静态页加托管结账页、没有 webhook 时无重放可测；一旦引入服务端，它立刻变成不可省。

## 落地动作

1. 四条测试卡逐条点一遍，每条截图存进 `docs/release/`。
2. 建一个最小额 SKU，用正式模式真实付一笔再全额退掉，确认到账时间与手续费损失（费率以官网当期价格为准）。
3. 跑两条 SQL 断言，都返回空才算通过。
4. 把「已付款但无权益」写进每日检查，上线后连查七天。
5. 记下每笔演练单的会话 ID，方便与后台对账。

## 常见坑

- **现象**：测试模式全绿，正式模式第一单没收到开通邮件 → **原因**：webhook 端点和密钥只配了测试版 → **对策**：正式模式小额单后查事件投递记录，不只盯支付状态。
- **现象**：退款后用户仍能访问内容 → **原因**：只处理了支付成功事件，没处理退款事件 → **对策**：退款事件写入回收时间，权限校验读这个字段。
- **现象**：同一订单发了两封开通邮件 → **原因**：事件重放时没有唯一键 → **对策**：唯一索引加重复事件直接返回成功。
