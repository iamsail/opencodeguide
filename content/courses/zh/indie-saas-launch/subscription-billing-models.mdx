订阅做复杂，多半不是因为客户要求，而是创始人觉得「以后可能要」。多一个计费维度就多一条同步链路、多一类账单争议，而这些在二十个客户之前不会带来一分钱收入。先把维度选对，再谈价格。

## 先定计费维度，再定额度

计费模型不是价格标签，它决定你要维护什么。

| 模型 | 适用条件 | 客户账单可预测性 | 你要维护的东西 | 主要代价 |
| --- | --- | --- | --- | --- |
| 固定月费 | 客户数少、成本主要是人力，边际成本接近 0 | 高 | 一个 recurring Price | 重度用户不付更多，轻度用户照付却流失 |
| 按席位 | 价值随人数增长（协作、权限、审计） | 高 | 成员数到订阅项 `quantity` 的同步 | 客户会共享账号来省席位 |
| 按用量 | 成本随调用、存储或时长近似线性变动 | 低 | 计量点、上报链路、幂等与对账 | 账单波动大，容易和客户吵 |
| 混合（底费 + 超额） | 有固定基础成本，同时有弹性用量 | 中 | 底价 Price 加阶梯超额 Price | 两层定价的解释成本最高 |

选择顺序是两个问题：成本是固定的还是随用量涨？客户能不能接受每月金额浮动？两个都模糊时选固定月费，把超额写进服务条款，而不是先写进计费系统。这个顺序能把「以后可能要」挡在数据库之外。

## 试用期是计费模型的一部分

试用不是「免费几天」，它决定三件事：试用结束时有没有卡可扣、转化发生在哪个事件上、扣款失败后怎么处理。

创建订阅时用 `trial_period_days` 给试用长度，是否强制先绑卡由 `payment_method_collection` 决定：`always` 要求结账时填卡，`if_required` 允许不填。允许不绑卡试用时，试用结束前必须有可用支付方式，否则订阅会停在无法续费的状态，而你往往在客户投诉时才知道。

拦截手段是 `customer.subscription.trial_will_end`：Stripe 会在试用结束前 3 天发送该事件，用它发一封绑卡提醒，比事后追款便宜得多。不带卡的试用能否提高转化，没有通用答案，判断方法是把同一流量分成两组各跑一批，看最终付费人数，别照抄别人的建议。

什么时候不用做试用：客单价低、决策周期短的产品，试用只是把付款往后推，直接给一段时间的退款承诺更简单，也更少一层客服成本。

## 席位同步与用量上报，错在这两处

席位计费的工作量不在 Stripe，而在你这边：成员增删要同步到订阅项的 `quantity`，升降级要处理按比例计费。漏同步的结果是客户付了 5 个席位、实际用了 12 个。

```ts
// 成员数变化后同步席位；调用方要保证可重放，重复设置为同一个值不会重复计费
await stripe.subscriptionItems.update(subscriptionItemId, {
  quantity: seats,
  proration_behavior: "create_prorations",
});
```

用量计费相反：金额由你上报，同一次调用被重试两次就多收一次钱。所以每条 usage record 都要带幂等键，重试时复用同一个键。

```ts
await stripe.subscriptionItems.createUsageRecord(
  subscriptionItemId,
  { quantity: units, timestamp: Math.floor(Date.now() / 1000), action: "increment" },
  { idempotencyKey: `usage/${requestId}` },
);
```

超额部分建议放在 Stripe 侧算：用 `billing_scheme: "tiered"` 加 `tiers_mode: "graduated"` 建一个阶梯 Price，比在自己的脚本里写分段函数可靠。代价是阶梯边界一旦公开就很难回调，定价页上要把档位写清楚。

## 落地动作

1. 用一句话写下成本结构。若每次请求的边际成本接近 0，就先排除按用量计费。
2. 在 Dashboard 建一个按月 recurring 的 Price，先用固定价上线，把「席位」与「用量」写进 roadmap 而不是数据库。
3. 要做席位时，在成员增删的同一事务之后触发 `subscriptionItems.update`，并加一个每日对账任务比对成员数与 `quantity`。
4. 用不绑卡试用的话，订阅 `customer.subscription.trial_will_end`，提前发绑卡邮件，并在订阅列表里标出即将到期且无支付方式的账户。

## 常见坑

- **现象**：客户投诉账单翻倍 → **原因**：同一批用量上报了两次，重试时没有幂等键 → **对策**：每条 usage record 带业务请求 id 作为 `idempotencyKey`，并保留上报日志供对账。
- **现象**：试用结束用户被静默停用，然后来投诉 → **原因**：试用期没绑卡，结束时没有可用支付方式 → **对策**：监听 `trial_will_end` 提前提醒，或直接改成先绑卡再试用。
- **现象**：席位加了三个，账单金额没变 → **原因**：成员变更只写了数据库，没有同步到订阅项 `quantity` → **对策**：把同步做成成员变更的必执行步骤，并用对账任务兜底。
