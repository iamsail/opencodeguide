坐下来想选题时，脑子里通常只剩「做个 AI 工具」这类抽象概念，因为真正的麻烦在你日常里发生，却从来没被记录。痛点在发生的那一刻最清晰，过了两天就退化成一句「有点麻烦」，再也估不出成本。

问题清单法的唯一要求是：只记录已经发生、并且让你付出了代价的事。

## 只记录有成本的痛点

一条记录必须能回答三个问题：什么时候发生的、当时你用什么办法绕过去了、为此花了多少时间或钱。

「绕过去」这个动作是关键。没有替代动作的抱怨，多半不是痛点——真正的痛点一定有成本，有成本就一定有人已经在凑合，而凑合的方式就是你未来产品的第一版。

反例：「客户管理很乱」不是痛点。「上周找不到三个月前那封报价邮件，翻聊天记录花了二十分钟」是痛点。

## 四个字段把抱怨变成候选需求

频率、单次成本、当前替代方案、谁付钱。前两个相乘得到「每周耗时」，这是排序依据；后两个决定商业模型。

替代方案要写具体：Excel、微信群、手写、雇人、干脆不做。它决定了你的替代成本有多高——如果对方现在的做法是「不做也行」，你卖不动。

谁付钱这一点最容易被跳过。受益者和付款人不是同一个人时（员工痛、老板付），客单价更高但销售周期更长，一个人的第一版优先选两者重合的场景。

## 五种需求来源的偏差不一样

自己想到的痛点最真，样本最小；社区里反复出现的抱怨样本大，但你不知道别人愿不愿意付钱。这张表用来判断一条信号该信到几分。

| 来源 | 说明什么 | 主要偏差 | 获取成本 | 适用阶段 |
| :--- | :--- | :--- | :--- | :--- |
| 自己的痛点 | 场景真实、细节完整 | 你可能只是少数派 | 零 | 起步首选 |
| 社群重复提问 | 有一群人卡在同一处 | 问的人未必付费 | 低 | 验证普适性 |
| 竞品差评 | 有人已经在付费且不满 | 差评者偏极端用户 | 中 | 找差异化切口 |
| 关键词搜索量 | 存在主动检索需求 | 搜了不等于会买 | 低 | 判断流量盘子 |
| 客户委托 | 已有人愿意为结果付钱 | 容易做成定制品 | 高 | 转产品化的最佳入口 |

前两种适合找方向，后三种适合判断这条路值不值得走。只用一种来源做决定，误判率最高。

## 七天七行，然后只留一条

不用建系统，一张表就够。字段固定下来，填的时候才不会自我美化。

```sql
create table if not exists pain_points (
  id           bigserial primary key,
  logged_on    date    not null default current_date,
  scene        text    not null,           -- 具体场景，不是抽象概念
  times_per_week numeric not null,         -- 一周发生几次
  minutes_each numeric not null,           -- 每次耗时
  workaround   text    not null,           -- 现在怎么绕过
  payer        text    not null,           -- 谁掏钱
  paid_before  boolean not null default false
);

select
  scene,
  round(times_per_week * minutes_each, 0) as minutes_per_week,
  payer,
  paid_before
from pain_points
where workaround <> ''
order by paid_before desc, minutes_per_week desc;
```

排序结果里，`paid_before` 为真的那条永远优先——已经为同类问题花过钱的人，不需要你教育。连续一周凑不满五条，说明你要么还没在真实场景里工作，要么这些麻烦确实不值钱，这时候该换场景而不是换文案。

## 什么时候不用做

手上已经有三个以上付费客户在等具体功能时，别再挖新痛点，把交付做完。清单法的用途是挑选题，不是无限期收集。

## 落地动作

1. 在数据库或表格里建上面那张表，每天收工前花三分钟补一行，连续七天。
2. 对排在前三的条目各写一句「谁，在什么场景下，为了避免什么损失，愿意每月付多少」，写不出金额的先降级。
3. 找三个同类角色的人，只问「你上次遇到这事是怎么处理的」，不要问「你会用吗」，然后用他们的真实做法替换你写的替代方案。

## 常见坑

- **现象**：清单里二十条全是「AI 帮我写 X」 → **原因**：记的是技术想象，不是发生过的场景 → **对策**：只允许写有具体日期和替代动作的条目，其余直接删。
- **现象**：频率很高但每次只花两分钟 → **原因**：把次数当价值 → **对策**：按每周耗时分档，低于三十分钟的进观察区，不做产品。
- **现象**：痛点是自己天天遇到的，做出来却没人买 → **原因**：你的场景依赖了别人没有的前置条件 → **对策**：先确认对方的工作流程里存在同一个触发点，再动手。
