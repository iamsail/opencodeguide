首屏写成功能清单，三行说完还没讲清给谁用；社会证明留了位置却没有内容，于是填一句「深受开发者喜爱」；定价摆了三档，用户问「我该买哪个」。这三处不是文案问题，是页面按研发顺序讲，而不是按用户的决策顺序讲。

## 首屏只回答三个问题

用户在第一屏只找三件事：这是什么、是不是给我用、下一步点哪。三句话答不完，后面基本不会被读到。

最小版本是一句话加一个按钮。描述里要出现目标角色和具体产物，比如「给独立开发者的支付接入检查清单」，而不是「提升效率的全新方式」。次级动作（看示例、进社群）用文字链接。

代价是看起来朴素，但这里做加法最贵：多一个轮播或视频，移动端首屏就被挤到折叠线以下，购买按钮跟着下沉。空间不够时先砍证据、再砍功能列表，最后动价值描述。

## 社会证明按阶段换素材

没有付费用户时，硬放 logo 墙和「1000+ 用户」是最快的信誉透支：数字一旦被追问就崩。

零用户阶段用可验证素材：公开的构建日志、代码仓库、可试用的示例产物、作者做过的具体项目。共同点是能被点开核实。代价是说服力弱，只解决「这人是不是认真在做」这一个疑问。

有十个用户后用原话引用，写清角色与场景并取得授权；上百个用户后才值得做聚合数据，且必须说清统计口径——否则用户默认你在编。

## 定价：档位数量是决策

单档适合单一交付物：一个价格、一次付款、一个结果。代价是接不住「只想试一下」和「要发票、要陪跑」两类人。

两档适合「自助」与「带人」的分野，用高价档给低价档做锚点。前提是你真能交付高价档，否则第一批高价用户就是第一批退款。

三档以上只在有企业采购或团队席位时成立，否则多出来的档只会让用户反复比较。

更容易出事的是价格来源：页面写 49、结账页显示 59，是最伤信任的失误。价格只留一份数据源，页面渲染与支付链接都从它读。

## FAQ 是退款前的最后一道防线

FAQ 不介绍功能，只把「付款后才会发现的事」说清：结算币种、交付时间与形式、退款窗口与申请方式、能否开票、内容有效期。

只收真实问题：最近十条客服咨询按频次排，取前五条；其余说明页面还缺信息，补在对应区块。

代价是页面变长。折叠收起，但退款与发票两条默认展开——它们直接决定退款率，藏起来省的空间要用退款来换。

## 决策表：区块顺序与出现条件

同一组区块，顺序不该固定。判断依据是用户来的时候对你了解多少。

```ts
type Section = "hero" | "proof" | "pricing" | "faq";

// 从订单表读，不要手写常量
const paidCustomers = 0;

const sections: Section[] =
  paidCustomers >= 10
    ? ["hero", "proof", "pricing", "faq"]
    : ["hero", "pricing", "faq"];
```

数据不够时整块不渲染，别放空壳占位符——「这里本该有内容」的空洞比没有更减分。

| 流量来源 | 首屏之后先放什么 | 适用条件 | 代价 |
| :--- | :--- | :--- | :--- |
| 冷流量（广告、推荐位） | 定价 + FAQ | 用户不认识你，先确认价格与退款 | 社会证明薄，转化全靠文案 |
| 搜索流量（长尾词） | 针对性证据段 | 搜索意图明确，要确认解决的就是他搜的问题 | 首屏得按关键词写，不能通用 |
| 社群与熟人流量 | 交付细节 + 社会证明 | 已有基础信任，关心内容和时间 | 对冷流量几乎无效 |

## 落地动作

1. 首屏改成一句话 + 一个按钮 + 一个证据，删掉第二段产品介绍。
2. 用 `sections` 常量替换硬编码顺序，数据不足时整块不渲染。
3. 价格写进 `content/courses/*.json`，页面与支付链接同源。
4. 翻最近十条客服记录，取前五条写进 FAQ，退款与发票默认展开。
5. 窄屏手机看一遍，确认购买按钮在首屏可见。

## 常见坑

- **现象**：页面写 49 美元，结账页显示 59 → **原因**：价格在两处硬编码，只改了一处 → **对策**：单一数据源，构建时校验页面与链接一致。
- **现象**：加了动效，停留时长涨了但购买点击没动 → **原因**：首屏没回答「给谁用」 → **对策**：价值描述加目标角色与具体产物。
- **现象**：FAQ 写了二十条，客服量没降 → **原因**：写的是想象中的问题 → **对策**：只收真实工单，按频次排序。
