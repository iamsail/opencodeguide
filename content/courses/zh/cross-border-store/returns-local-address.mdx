把退货政策写宽松，是提升转化最快的手段之一。但如果政策里只有一句「支持退货」而没有地址，它实际制造的是一个死循环：客户想退，退回原产国的运费接近甚至超过货值，于是他去开争议，而不是来问你。

## 没有地址的退货政策等于没有政策

在客户的理解里，「支持退货」等于「我在本地就能退」。一旦发现要跨境寄回，他只有两条路：放弃并开争议，或者自费寄回再向你要运费。两条路都通向拒付，而拒付在你的账户上留下的记录，比一次退款贵得多。

本地退货地址因此有两层价值：一层是履约成本（退回来的货能二次销售），另一层是转化与风控（客户看到本地地址更敢下单，争议时你有一个可执行的处理路径）。

## 三种处置方式的成本排序

| 处置方式 | 单次成本 | 二次销售可能 | 运营复杂度 | 适合 |
| :--- | :--- | :--- | :--- | :--- |
| 本地退货地址 | 入库 + 检测 + 仓储 + 二次发货 | 高，可分级折价 | 高，需要 3PL 与质检标准 | 货值高、可翻新、SKU 稳定 |
| 退款不退货 | 全额货值，无物流成本 | 无 | 低，一条规则即可 | 货值低、退回运费占比过高 |
| 部分退款 | 折扣金额 | 无，货留在客户手里 | 低，但需要话术 | 轻微瑕疵、尺寸偏差、客户想留 |

排序的关键不是绝对金额，而是「退回后还能收回多少」。同样一批退货，能按原价七成再售和只能按三成清仓，结论完全不同。

## 退款不退货的临界点

```ts
// 退回净回收 = 可再售价格 − 处理成本。为正才值得要求寄回
function netRecovery(p: {
  resalePrice: number;      // 质检后能卖出的价格，不是原售价
  returnShipping: number;   // 退回运费，谁付都计入总成本
  inspection: number;       // 入库检测、清洁、换包装
  storageMonths: number;
  storagePerMonth: number;
}): number {
  const cost = p.returnShipping + p.inspection + p.storageMonths * p.storagePerMonth;
  return p.resalePrice - cost;
}

type Decision = "request_return" | "refund_only" | "partial_refund";

// 轻微瑕疵优先给部分退款：省下双向运费，客户也保住了「占到便宜」的感觉
export function decide(input: {
  condition: "like_new" | "minor_defect" | "damaged";
  netRecovery: number;
  goodWillCap: number;      // 你愿意为省事付出的折扣上限
}): Decision {
  if (input.condition === "minor_defect" && input.goodWillCap > 0) return "partial_refund";
  return input.netRecovery > 0 ? "request_return" : "refund_only";
}
```

退款不退货会被滥用，防护不靠人工审核，靠规则：同一收货地址或同一账号在一定周期内的次数上限、金额上限，超过就转人工。规则写在代码里，客服不需要临场判断。

## 退货率控制在售前

退货原因必须结构化，否则你无法归因。最小的一套原因码：尺码或规格不符、与描述或图片不符、运输破损、不需要了、物流太慢。每个码对应一个售前动作，例如「尺码不符」对应尺码表与模特身高体重的实拍，「与描述不符」对应材质说明与色差提示。

按 SKU 和市场拆开看，问题往往集中在少数几个 SKU 上。先修这些，比全局改文案便宜得多。另一个常被忽略的分母：退货率的分母是发货量还是签收量，两者算出来的数不一样，对外沟通和内部考核必须统一。

## 小团队的最小可行版本

一个本地退货地址（可以先按件付费借用 3PL 的退货服务，不必自建）、三条退款规则（低货值直接退、轻微瑕疵部分退、高货值必须退回）、一张原因码表。这三样东西一个下午能配完，覆盖大部分场景。

什么时候可以不做本地退货地址：客单价低到退回不划算、退货率本来就极低、或者品类本身不可退（个护、食品、定制）。此时把「退款不退货」写成明确政策，比含糊承诺更省事。

## 落地动作

1. 在配送与退货政策页写清：退货窗口、退回地址在哪个国家、谁承担退回运费、退款多久到账，中英各一版。
2. 给最近一批退货订单打原因码，按 SKU 汇总，找出占比最高的一个原因，去对应修改那一页商品详情。
3. 用 `netRecovery` 算你销量前三的 SKU 的临界值，把它写成客服可查的三档退款规则。
4. 设定滥用防护规则：同一地址或账号的申请次数与金额上限，超过转人工，并记录在订单备注里。

## 常见坑

- **现象**：退货政策写着「支持退货」，争议率却没降 → **原因**：没有本地地址，客户算完成本直接放弃并开争议 → **对策**：给出本地退回地址与承运方式，争议时作为你已提供解决方案的证据。
- **现象**：退款不退货被少数客户反复使用 → **原因**：规则只按金额判断，没有按地址、账号、频次约束 → **对策**：加上频次与地址维度，超限转人工，并在条款里写明滥用处理方式。
- **现象**：退货率突然上升，找不到原因 → **原因**：原因码是自由文本，无法聚合 → **对策**：改成固定枚举加一个备注字段，按周汇总，先看占比最高的那一个。
