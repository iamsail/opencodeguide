把「七天到货」写进商品页，是跨境纠纷最常见的起点之一。它不是任何一家物流商的承诺：揽收、出境、清关、尾程派送四段里，只有最后一段真正由物流商支配。

## 报价单只回答了一半问题

报价单给的是单价和一句「参考时效」。签约前必须书面确认四件事：时效从哪一刻起算（揽收扫描还是出境）、计费重系数与附加费项（偏远地区、超规、旺季）、丢件与破损的赔付上限及索赔材料、状态码清单与回传方式。

四项里任何一项含糊，后面都会变成客服成本。赔付上限尤其要看清：它通常按申报价值或按票封顶，与客户主张的金额不是一回事，差额要提前算进毛利。

| 要问到的口径 | 不合格的信号 |
| :--- | :--- |
| 时效起算点与统计方式 | 只说「一般几天」，给不出分市场数据 |
| 计费重系数、附加费清单 | 只给首重续重价，附加费「到时候再看」 |
| 赔付上限、索赔时限与材料 | 口头承诺「丢了全赔」 |
| 状态码文档、回传频率与方式 | 只能人工查单，没有查询接口 |

## 时效是分布，承诺要写区间

同一线路的签收天数是分布，不是平均数。用历史订单算出分布，取一个你愿意负责的分位（取值取决于客单价与赔付政策），写成「预计 X 到 Y 个工作日」，并让商品页、结账页、确认邮件、追踪页保持同一口径。

一个承诺覆盖所有市场，等于按最差的市场持续赔付。分市场写，是成本最低的风险隔离。

## 追踪页：把承运商状态翻译成你的状态

不要直接透传原始状态码。客户看到 `Customs clearance delay` 只会做一件事：开争议。你需要一个语义少、可解释的状态集合和一张显式映射表。

```ts
type OrderStatus = "shipped" | "in_transit" | "out_for_delivery" | "delivered" | "exception";

// 未命中的状态一律落到 in_transit：宁可少报，也不要在客户面前误报
const carrierToInternal: Record<string, OrderStatus> = {
  PICKED_UP: "shipped",
  DEPARTED_ORIGIN: "in_transit",
  ARRIVED_DESTINATION: "in_transit",
  CUSTOMS_HOLD: "exception",
  OUT_FOR_DELIVERY: "out_for_delivery",
  DELIVERED: "delivered",
  RETURNED_TO_SENDER: "exception",
};

// 超过你承诺的区间上限仍未签收，自动升级为异常并推给客服
export function resolveStatus(raw: string, daysSinceShip: number, promisedMaxDays: number): OrderStatus {
  const mapped = carrierToInternal[raw] ?? "in_transit";
  if (mapped !== "delivered" && daysSinceShip > promisedMaxDays) return "exception";
  return mapped;
}
```

映射表放在代码里而不是客服文档里：改一次全站生效，下单、发货、追踪三条链路共用一套定义。

## 异常件需要一条默认路径

异常分三类，处理方式完全不同：清关滞留（通知客户补资料，话术与时限固定）、地址错误或客户拒收（先联系确认，不要直接退回，退回来的运费往往比货值高）、长时间无更新（超过承诺上限即触发，不等客户来问）。

每类写清五件事：触发条件、由谁处理、首次响应时限、是否赔付、赔付口径。写成一张表，值班的人不需要判断力也能执行。

## 小团队的最小可行版本

主备两家按线路分配，不要把单量平均拆开：平均分单会同时失去两家的价格档与处理优先级。追踪页自己渲染，映射表进代码，异常件用一张表加三条话术。

什么时候可以不做：单量小、市场少、客单价低到人工处理异常比自建追踪页更便宜时，先人工。追踪页也可以先用物流商现成的查询页，但邮件里要写明以我方通知为准。

## 落地动作

1. 导出过去三个月的订单，算揽收到签收的天数分位，不要只算平均值，把分市场的结果记下来。
2. 向每家候选物流商逐条确认上表的四个口径，把对方的书面回复存档，口头承诺不算。
3. 把 `resolveStatus` 落进发货流程，未命中状态默认 `in_transit`，超期自动标异常。
4. 写三条异常话术，覆盖补资料、地址确认、超期未达，放进客服快捷回复。

## 常见坑

- **现象**：承诺七到十五天，第十天客户就开始开争议 → **原因**：承诺用的是均值，且全程没有主动通知 → **对策**：按分位写区间，并在出境、清关完成、派送三个节点主动发邮件。
- **现象**：换了一家更便宜的物流商，投诉率反而上升 → **原因**：只比了运费，没比状态回传质量与清关能力，问题件全部转成客服工时 → **对策**：把状态码完整度、更新频率、清关异常处理能力纳入选型评分，价格只占一部分权重。
- **现象**：追踪页显示已签收，客户说没收到 → **原因**：尾程派送商的签收口径（代收点、前台、门廊）与你的理解不同 → **对策**：要求提供签收凭证，并在提交争议时作为证据；高风险订单额外要求签名服务。
