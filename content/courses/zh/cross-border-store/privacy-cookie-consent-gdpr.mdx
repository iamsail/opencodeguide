「等做大再补隐私页」的代价不是罚款，而是补不回来的合法基础：广告像素已经在用户没同意时跑了好几个月，那些数据删也不是、用也不是。独立站还多一层麻烦——一笔订单要经过支付、物流、广告三条链路出境，每条都是数据出口，多数人却只写了第一条。

## 独立站比 SaaS 多两条数据出口

| 链路 | 流出去什么 | 接收方 | 常见误区 |
| :--- | :--- | :--- | :--- |
| 支付 | 邮箱、账单地址、卡信息 | 支付服务商 | 以为卡号经过自己服务器 |
| 物流 | 收件人姓名、地址、电话 | 货代、承运商、清关行 | 面单信息没写进隐私政策 |
| 广告 | 页面行为、转化事件、Cookie 标识 | 广告平台 | 像素在同意前就加载 |
| 分析 | 页面、设备、来源 | 分析服务 | 分不清必要与非必要 |

支付这条先说清「谁来收集」：托管结账页由支付方直接收卡号，你的合规范围小得多；自建表单收卡号，范围立刻扩大，还要承担对应的安全义务。这是架构差异。

物流那条最常被漏：收件人信息要经货代、承运商、清关行，这些接收方都该出现在处理者清单里。判断方法很实在——翻一遍实际发出的邮件与面单，能对上的才写。

## Cookie 同意只在有非必要脚本时才是问题

标准只有一条：这个 Cookie 是不是完成用户请求所必需。登录态、购物车、结账会话、防伪令牌属于必要；统计、广告归因、再营销属于非必要，需要事前同意且能撤回。

关键在「事前」：脚本必须在同意后才发起请求。先加载再弹横幅等于没有同意，数据已经出去了。实现上别用「同意后整页 reload」，而是在注入前判断状态。

```ts
// consent.ts —— 只在对应类别获得同意后注入脚本；撤回时停用并清标识
export type Category = "analytics" | "ads";

const LOADERS: Record<Category, () => void> = {
  analytics: () => { /* 注入 GA4 或自托管分析 */ },
  ads: () => { /* 注入广告像素，不要在 <head> 里静态引入 */ },
};

export function applyConsent(state: Partial<Record<Category, boolean>>) {
  for (const [key, load] of Object.entries(LOADERS)) {
    if (state[key as Category]) load();
  }
  // 撤回同意：清掉已写入的标识，并让后续事件不再上报
  if (!state.ads) document.cookie = "_fbp=; Max-Age=0; path=/";
}
```

代码的价值不在写法，而在它强迫你先给脚本分类：分类不清，买什么同意管理平台都只是装饰。具体 Cookie 名以实际投放的工具为准。

## 数据跨境：先能答出「数据存在哪」

监管问的第一个问题通常不是「有没有政策」，而是「数据在哪、依据是什么」。每个服务商都要能说清：存哪个区域、走什么传输机制、有没有签数据处理协议。

没有技术捷径，只有一张表：服务商、用途、字段、存储区域、传输依据、协议状态。依据看信任中心与子处理者列表，不看销售页。代价要提前算：区域化存储往往更贵或功能更少，换服务商要重做一遍集成。

## 一个人的最小实现只有四件事

1. 隐私政策按实际出网请求写，写不准的部分宁可删功能。
2. 非必要脚本全部走同意门控，并提供撤回入口。
3. 一条按邮箱聚合的导出 SQL、一条匿名化删除 SQL，能在时限内跑完。
4. 退订链接可用，并识别浏览器发来的全局隐私信号。

再加一件：把数据保留期写进定时清理任务。没有保留期等于永久保存，而永久保存既是风险也是成本。

## 什么规模可以只做前两件

订单还是个位数、没投广告时，只需两件事：政策页写准、不加载非必要脚本。没有要征求意见的东西，就不需要横幅。

装了像素或多渠道归因再上同意管理平台；有企业客户或 B2B 询盘时，再补处理者协议与传输依据。反过来做——先买平台再想分类——是最常见的浪费。

## 落地动作

1. 打开 Network 面板走一遍「加购到支付成功」，把每个第三方域名记下来。
2. 用这份清单写 `content/legal/processors.yaml`，只填能说出用途的。
3. 把 `consent.ts` 落进项目，确认拒绝状态下广告域名完全不出现。
4. 用测试订单跑一遍导出与删除，记录耗时，确认在时限内完成。

## 常见坑

- **现象**：装了同意横幅，欧盟用户仍投诉被追踪 → **原因**：像素写死在 `<head>`，横幅只是遮罩 → **对策**：脚本动态注入，拒绝时不发请求，并在政策里说明撤回方式。
- **现象**：用户要求删除，主库删了却仍收到营销邮件 → **原因**：邮箱还留在邮件服务商与分析工具里 → **对策**：把删除写成清单，逐个系统清理并留记录。
- **现象**：隐私政策列了十几家服务商，一半没在用 → **原因**：抄了同行清单 → **对策**：按实际出网请求与账单倒推，只写能对上用途的。
