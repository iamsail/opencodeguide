欧洲订单失败后出现 `authentication_required`，最常见的处理是去后台把 3DS 关掉。关掉之后验证页确实不再弹，但交易还是过不去：对欧洲经济区与英国的持卡人，强客户认证是监管要求，不是商家的可选项。真正能操作的是在合规框架里压低挑战率，不是把验证关掉。

## 先判断「这笔订单归谁管」

看的是买家账单地址与发卡行所在辖区，不是你的公司注册在哪。欧盟的 PSD2 由各成员国立法落地，英国脱欧后有独立的一套，各国对豁免清单的解释与执法严格程度也不一致——具体适用范围与执行口径以当地监管机构、以及 EBA 的公开指引与问答为准，不要背一份清单当事实。

写代码时的分支就应该是「买家账单国家是否属于 SCA 辖区」。辖区内的交易不做验证，结果是被发卡行拒掉，或者即使成功也拿不到责任转移；辖区外的交易强制验证，只是白多一步摩擦。

## request_three_d_secure 的三个取值

| 取值 | 谁决定是否挑战 | 挑战率 | 适合的阶段 |
| :--- | :--- | :--- | :--- |
| `automatic` | Stripe 结合风险信号与发卡行能力判断，符合条件的交易走豁免、直接免验证 | 最低 | 默认值，几乎所有阶段 |
| `any` | 只要卡支持 3DS 就发起挑战，不主动申请豁免 | 高 | 拒付率偏高、客单价高、账户已被风控关注 |
| `challenge` | 放弃豁免，全部交易挑战 | 最高 | 只在明确知道自己拿转化换什么时用 |

`automatic` 依赖数据质量：账单地址、历史交易、设备与浏览行为。新账户、新客、地址缺失时，可用的豁免依据少，挑战自然变多——这不是配置错了，是数据不够，硬切 `any` 只会更差。

3DS 真正的价值不是「更安全」，是责任转移：验证通过后，`fraudulent` 类拒付的责任转到发卡行，你几乎不必举证。欺诈高发的品类里，多付挑战率换它划算；低风险品类里让 `automatic` 替你判断更划算。

## 成功率要按失败码拆开看，不要看一个总数

只有一个「支付成功率」时，你分不清损失来自技术、用户还是发卡行。按 `decline_code` 分组，三类问题解法完全不同：

| decline_code | 谁的问题 | 动作 |
| :--- | :--- | :--- |
| `authentication_required` | 你的集成没做验证 | 打开 `automatic`，别在结账页用自建风控先拦一道 |
| `authentication_not_handled` | 用户在银行页面超时或关闭 | 保留订单，发一封带重试入口的邮件，不要立刻取消 |
| `authentication_failed` | 验证本身没通过 | 提示换卡或换支付方式，同一张卡重试没有意义 |
| `do_not_honor` | 发卡行策略性拒绝 | 引导换卡；反复重试同一张卡只会积累失败记录 |
| `insufficient_funds` | 余额不足 | 提示稍后重试，不要计入风控失败 |
| `processing_error` | 技术问题 | 可有限次自动重试 |

每周看一次这张表：`authentication_*` 上升说明验证链路有洞，`do_not_honor` 集中说明目标市场的发卡行对你不友好，前者改代码，后者改市场与支付方式组合。

## 挑战页之外还能做的两件事

一是把账单地址收完整。地址缺失会让更多交易失去豁免依据，也让 AVS 无从校验。

二是状态别丢。验证发生在银行域名下，用户回来时可能已换设备或超时，本地草稿和 `client_reference_id` 要还在，否则就是「钱扣了、订单没了」的客服单。

## 什么时候可以不做

只卖北美与东南亚、客单价低、拒付里几乎没有 `fraudulent` 的店，不做 3DS 也能正常收款，先别为它改架构。判断依据不是感觉，是按买家国家统计失败码：`authentication_required` 一旦集中出现，说明有真实买家被挡在门外，这时才值得动集成。

用托管结账页（Stripe Checkout / Payment Link）时，跳转与豁免都由 Stripe 处理，你只要确认账户的 3DS 设置没被关掉；自己用 Payment Element 搭，才需要处理 `next_action` 的跳转与回跳恢复。

## 落地动作

1. 显式声明 3DS 策略，别依赖账户默认值哪天被改：

```bash
curl -s https://api.stripe.com/v1/payment_intents \
  -u "$STRIPE_SECRET_KEY:" \
  -d amount="$AMOUNT_MINOR" \
  -d currency=eur \
  -d "payment_method_options[card][request_three_d_secure]=automatic" \
  -d "automatic_payment_methods[enabled]=true" \
  -d "metadata[order_id]=$ORDER_ID" \
  | jq '{id, status, next_action: .next_action.type}'
```

2. 把失败交易按失败码拉出来看一眼，不用等周报：

```bash
curl -s -u "$STRIPE_SECRET_KEY:" \
  "https://api.stripe.com/v1/payment_intents?limit=100" \
  | jq -r '.data[]
      | select(.status == "requires_payment_method")
      | (.last_payment_error.decline_code // "unknown")' \
  | sort | uniq -c | sort -rn
```

3. 用 Stripe 官方 testing 文档里那张「需要验证」的测试卡，在测试模式完整走一遍挑战、通过、回跳，确认订单状态与收据都没断。

## 常见坑

- **现象**：测试环境一路通，真实欧洲订单却大量失败 → **原因**：测试卡不经过发卡行的地区风控与豁免判断，本地成功不代表当地持卡人能过 → **对策**：在目标市场用一张真实小额订单验证一次完整链路，再看失败码分布。
- **现象**：关掉 3DS 后欧洲拒付明显变多 → **原因**：没有验证就没有责任转移，`fraudulent` 类拒付全落在你身上，举证也基本赢不了 → **对策**：恢复 `automatic`，把「欧洲要不要做验证」当成准入问题而不是转化问题。
- **现象**：为提成功率切到 `any`，挑战率上去了、拒付率没降 → **原因**：老客与低风险交易本可豁免，被一起推去挑战，白付摩擦成本 → **对策**：回到 `automatic`，或对新客与老客分层配置，只在高风险客群收紧。
