复购低的时候，最诱人的方案是上一个订阅：把一次性收入变成每月收入，报表立刻好看。但订阅不是商业模式，它是「交付节奏可预测」这件事的变现方式。品类不具备这个前提，订阅只会带来更高的流失率与更重的客服。

## 三条路径的前提不同

| 路径 | 机制 | 适合的品类 | 主要风险 | 验证指标 |
| :--- | :--- | :--- | :--- | :--- |
| 捆绑 | 提高单次客单价 | 互补品、凑单场景 | 折扣侵蚀毛利 | 捆绑客单价 ÷ 单品客单价 |
| 会员 | 预付费换长期权益 | 高频复购、运费敏感 | 权益兑现成本失控 | 会员续费率 |
| 订阅 | 周期性交付 | 耗材、持续消耗 | 流失与拒付累积 | 队列留存曲线 |

先判断复购动机：是「用完了要再买」，还是「想起来才买」。前者适合订阅，后者适合会员或捆绑；把「想起来才买」做成按月扣款，第三个月就会集中退订。

## 捆绑：提客单价，不改变复购

捆绑解决的是单次订单价值，不是留存。有效的前提是互补而非同类替代：买了刷头需要清洁液，买了主机需要耗材。

`捆绑毛利率 = (捆绑价 − 组合商品成本 − 组合履约) ÷ 捆绑价`

组合履约常被忽略：两件商品合单发货省下的运费要算进去，分开发货的额外成本也要算。捆绑价必须让「捆绑毛利率 ≥ 单品毛利率 − 可接受折让」，否则只是用毛利换成交额。

## 会员：卖的是未来会用的权益

会员费本质是预收现金，代价是承诺。权益要选边际成本低的：免运费、专属价、提前购、延长退换。每一项都要能算出年化成本上限，否则重度用户会把权益用穿。

`会员盈亏平衡点 = 会员年费 ÷ 单次权益平均成本`

超过这个次数，会员就在亏钱。所以要么设使用上限，要么把权益设计成低成本项（如提前购、内容、售后优先）。

## 订阅：先用留存曲线算，再谈规模

`订阅 LTV ≈ 客单价 × 毛利率 ÷ 月度流失率`，这是忽略折现的近似值，用来做量级判断。

`CAC 回收期 = CAC ÷ (客单价 × 毛利率)`

回收期长于现金流能撑的月数时，增长越快越危险。流失率要用队列观察，不要用「本月取消数 ÷ 本月订阅数」——分母里混着新订阅，会算出偏低的流失。

## 在 Stripe 上落地

订阅用 Stripe 的 recurring price 与 Billing，会员用一次性付款加到期时间字段。本站是静态导出部署在 GitHub Pages，没有 Node 运行时，所以权益状态必须由 webhook 写入数据库，再由页面读接口校验：

```json
{
  "entitlement": "member",
  "source": "stripe",
  "verify": {
    "webhook": ["checkout.session.completed", "invoice.paid", "customer.subscription.deleted"],
    "store": "customer_email -> {plan, status, current_period_end}",
    "client": "只读接口结果，不读 localStorage 判断是否会员"
  },
  "reject_if": ["status != active", "current_period_end < now"]
}
```

浏览器里的标记只能用来做 UI 提示，不能用来解锁内容或折扣——它能被改。

## 落地动作

1. 用最近 12 个月的订单算复购间隔分布，判断你的品类是「用完再买」还是「想起来才买」，据此选一条路径。
2. 对选定路径写出成本模型：捆绑算组合履约，会员算权益年化成本上限，订阅算回收期。
3. 在 Stripe 建一个测试价格，用 webhook 落库跑通一次权益校验，确认改前端状态无法绕过。

## 常见坑

- **现象**：上线订阅后，前三个月增长漂亮，第四个月开始净流失。→ **原因**：品类复购节奏不支撑按月扣款，用户在用完前就取消。→ **对策**：改按消耗周期计费，或退回会员与捆绑。
- **现象**：会员卖得很好，客服与运费成本同步上涨。→ **原因**：权益边际成本没算，重度用户把免运费用到极限。→ **对策**：给权益设上限，或换成低成本权益。
- **现象**：订阅用户在前端能看到会员内容，续费失败后仍然能看。→ **原因**：权益判断放在浏览器，webhook 失败没有兜底。→ **对策**：权益只认服务端记录，webhook 事件补查询，过期即失效。
