很多人在 Shopify 后台找「结账页模板」，翻到的是购物车，不是结账。结账页从来不属于主题，这个误解通常要花掉两三天，而且是在你已经对外承诺上线日期之后。先把三套机制的边界分清，定制才不会白做。

## 主题、购物车、结账是三套机制

- **主题**（Liquid 与 Online Store 2.0 的 sections/blocks）：负责商品页、集合页、购物车页或抽屉、内容页。改样式、加信任条、做捆绑展示都在这里。
- **结账**：由平台托管的独立应用，只开放品牌化与扩展点，主题的资源不会加载进结账。旧的 checkout.liquid 做法适用范围已经收窄，开放计划与截止时间以官方 changelog 为准，不要按教程里的旧结论排期。
- **Checkout Extensibility**：四类能力——UI 扩展在文档规定的位置插入组件，Branding API 控制样式与排版，Web Pixels 负责埋点，Shopify Functions 在服务端做折扣、配送与支付方式的定制和校验。

## 结账里值得改的四件事

1. **支付方式排序与隐藏**：按国家、币种、订单金额或会员标签决定哪些方式出现，减少「选了却付不了」的失败。
2. **配送选项改名与隐藏**：把「标准配送」改成带时效的文案，隐藏不适用地区的选项。
3. **结账内提示**：预计到货、退货政策、关税与税费说明，降低犹豫，也降低售后争议。
4. **拦截与校验**：高风险邮编、超重、禁售地区直接拦住，比事后退款便宜。

| 想达成的效果 | 该用的机制 | 硬边界 |
| --- | --- | --- |
| 改结账页配色与字体 | Branding API | 品牌配置以版本发布，回滚要重发 |
| 在结账页插一行到货说明 | UI 扩展，绑定指定 target | 只能插在文档开放的点位 |
| 按国家隐藏支付方式 | 支付定制（Function） | 只能排序、改名、隐藏，不能新增方式 |
| 按超重或邮编拦截下单 | 购物车或结账校验（Function） | 拦截必须给用户看得懂的提示 |
| 统计结账漏斗 | Web Pixels | 不能塞任意第三方脚本 |
| 在店面加信任条 | 主题 section | 结账不加载主题资源，改了不生效 |

前两件是减少误选，第三件是减少犹豫，第四件是风控。不要为了好看改结账：结账页每多一个字段、每多一次跳转，就多一次放弃。优惠券输入框、备注框这类「看起来有用」的元素，往往是可以删的。

## 扩展的工程约束

扩展跑在沙箱里，只有官方组件与 API，不能操作 DOM，也不能塞第三方脚本。需要额外行为时调用你自己的后端，但要按「结账页不能等」来设计：超时就降级为不显示，而不是转圈等结果。埋点走 Web Pixels，别指望在扩展里塞像素代码。

发布以 app 版本为单位，UI 扩展与 Functions 的可用计划并不相同，上线前逐个核对文档里的计划标注；回滚就是把旧版本重新发布，所以每次发布都要记下版本号。

```bash
shopify app dev              # 本地起预览，改完热更新
shopify app deploy           # 发布新版本（UI 扩展与 Functions 一起）
shopify app versions list    # 记下可回滚的版本号
```

```toml
# extensions/checkout-delivery-note/shopify.extension.toml
# api_version 与 app 的 API 版本保持一致，不要单独升扩展
[[extensions]]
type   = "ui_extension"
name   = "checkout-delivery-note"
handle = "checkout-delivery-note"

  [[extensions.targeting]]
  module = "./src/Checkout.tsx"
  # 点位以官方 target 列表为准，不同计划开放的点位不同
  target = "purchase.checkout.delivery-method.render-after"
```

## 什么时候不做这些

单量小、支付方式只有卡、目标市场单一，结账定制的收益远小于维护成本，把时间放在商品页与素材上更划算。等出现「某些国家老是支付失败」「客服反复解释运费」这类具体问题时再改，那时你确切知道该改哪一处，也能量出改前改后。

## 落地动作

1. 打开官方文档，把目标效果逐条映射到机制，写下每个扩展点在你的计划上是否开放。
2. 在开发店只做一件事：在配送方式下方加一行预计到货说明，跑通「改代码 → 预览 → 发布」。
3. 给结账内每个网络请求设超时与降级，失败时不阻塞下单。
4. 发布前记录 app 版本号，并演练一次回滚。

## 常见坑

- **现象**：改了主题 CSS，结账页毫无变化 → **原因**：结账不加载主题资源 → **对策**：用 Branding API 或扩展，不要试图用主题影响结账。
- **现象**：扩展上线后下单失败率上升 → **原因**：在扩展里同步调用自己的接口且没有超时 → **对策**：设超时并降级为隐藏，关键校验放 Functions。
- **现象**：开发者店能跑，正式店扩展点不出现 → **原因**：该点位在正式店的计划上不开放 → **对策**：核对文档标注，换到开放范围内的点位。
